# The two-station explorer

`codegen/src/Packet.Sdl.Explorer` composes two reference-interpreter Data Link machines (`Packet.Sdl.Interpreter`, station A and station B) over a modelled channel and explores every interleaving breadth-first from a seeded state, checking cross-station invariants after every step. It is steps 2 and 3 of the decision brief `packethacking/ax25spec` `docs/fuzzing-the-figures.md`: the calibration suite that proves the invariants have teeth by rediscovering known figure defects, and the two-station progress model built on the interpreter from #75.

Breadth-first means the first counterexample found is the shortest. Every counterexample prints as a step log: which station, the injected event with its fields, the transition id that fired, the effects emitted, and both stations' key variables after the step.

Run it:

```sh
dotnet run --project codegen/src/Packet.Sdl.Explorer -- --tables spec/json --frames-ab 2 --frames-ba 0 --k 4 --srej --budget 1 --faults drop,dup
dotnet run --project codegen/src/Packet.Sdl.Explorer -- --frames-ab 2 --flow-control B                      # #43 in three steps
dotnet run --project codegen/src/Packet.Sdl.Explorer -- --frames-ab 0 --seed awaiting-v22 --peer v20-frmr --selective-progress   # #45 in four
dotnet run --project codegen/src/Packet.Sdl.Explorer -- --frames-ab 0 --seed awaiting-v22 --peer v20-dm     # #48 in two
dotnet run --project codegen/src/Packet.Sdl.Explorer -- --help
dotnet test codegen/tests/Packet.Sdl.Explorer.Tests        # the calibration suite
```

A second checker, TLC over a TLA+ model generated from the same JSON tables, reproduces this explorer move for move and is compared with it row by row: see `docs/tla.md`.

Exit code 0 means no violation in the exhaustively explored bounded space, 1 means an invariant fired (the counterexample is printed), 2 means a depth or visited-state bound was hit before the space was exhausted (the liveness checks were skipped; this is never reported as "no violation").

## The model

**System state.** Both machines' full state (state name, V(s)/V(r)/V(a), RC, flags, I-frame queue with its retransmission bookkeeping, saved out-of-sequence frames, retained sent frames, T1/T3 symbolic status), the two channel queues (frames in flight A to B and B to A, each an ordered list of concrete frames: type, command/response, P/F, N(r), N(s), payload label), each station's owed `LM_SEIZE_confirm`, the remaining fault budget, the delivery and acknowledgement counters the invariants need, each station's layer-3 flow state ("flow off" flag and completed FLOW_OFF/FLOW_ON rounds), and, when station B is the v2.0 stub peer, whether the stub is connected. A canonical serialisation of all of it is the key of the visited set.

**Enabled moves** (each is one BFS edge):

- deliver the head frame of either channel to its receiver as the matching `*_received` event with `pf`, `command`, `nr`, `ns`, `data` filled in from the frame and the environment atoms `able_to_establish` = true, `info_field_length_le_N1_and_content_is_octet_aligned` = true;
- a channel fault on a head frame while the budget lasts: drop it, duplicate it (deliver it and leave a copy at the head), or reorder (swap the first two). Each kind is switchable (`--faults drop,dup,reorder`); `--drop-scope interior-i` restricts drops to I frames that are not the last submitted in their direction;
- `I_frame_pops_off_queue` at a station whose queue is non-empty, but only when the pop changes something (a window-full or peer-busy pop pushes the frame straight back and is a self-loop);
- `LM_SEIZE_confirm` at a station that owes one;
- `T1_expiry` at a station whose T1 is running, only when both channel queues are empty, no confirm is owed and no productive pop is pending anywhere: the quiescent-timeout abstraction. A timer fires only once everything in flight has been delivered or lost. This keeps the space finite and is sound for the progress properties, and it loses premature-timeout interleavings (a T1 that fires while frames are still on the air);
- `DL_FLOW_OFF_request` and `DL_FLOW_ON_request` at a station the scenario lets layer 3 flow-control (`--flow-control A|B|both`), only on a page with a direct arm for them (Connected, TimerRecovery: layer 3 does not flow-control a link that is not up). FLOW_OFF is enabled once the station has delivered `--flow-off-after` frames upward (default 1) and a round is left; FLOW_ON is enabled whenever flow is off; FLOW_OFF then FLOW_ON is one round and `--flow-rounds` (default 1) bounds the rounds so the space stays finite. The simple shape "B turns flow off once after its first delivery, then on again later" is the default. Neither move is a fault, so the liveness checks may use them; neither affects the quiescent-timeout rule (a layer-3 decision is not work in flight);
- with `--data-after-confirm` (disconnected seed only), `DL_DATA_request` for a station's next frame once its data link has reported the link up to layer 3 (`DL_CONNECT_confirm` at A, `DL_CONNECT_indication` at B), one frame per move, in order. Layer 3 stops submitting when its data link reports the link down (`DL_DISCONNECT_indication` or `DL_DISCONNECT_confirm`) and resumes, with its next unsent frame, after the next `DL_CONNECT_confirm` or `DL_CONNECT_indication` (pinned semantic 13). It is not a fault, so the liveness checks may use it; a station with a frame ready to submit counts as pending work for the quiescent-timeout rule, so T1 does not fire past it;
- with `--data-before-confirm` (`ExplorerOptions.DataBeforeConfirm`, which implies `--data-after-confirm`), A's layer 3 does not wait for its confirm: it treats the link as usable from the seed on, so its submissions are moves that can come before the UA (where figc4.2 discards them while layer 3 initiated, ax25spec#161) or after it. B's layer 3 still waits for its indication. This is the move form of the `d161-data-before-confirm` seed;
- with `--release A|both` (`ExplorerOptions.Release`), `DL_DISCONNECT_request` from that station's layer 3 (or either station's), once, on an established link (Connected or TimerRecovery, the pages with a direct arm for it), once every frame either station submitted has been delivered upward at its peer: the application knows the exchange is complete. It is not a fault, so the liveness checks may use it. Like flow control it is a layer-3 decision, not work in flight, so it does not hold back T1. Quiescence then means released: both stations Disconnected after a layer 3 issued its release, nothing in flight or queued, everything delivered, no owed confirms. Table-driven peer only. A consequence worth knowing: the release masks #91 (H1 below), because it takes a stranded station out of TimerRecovery, so a release scenario cannot see #91;
- with `--release-early` (`ExplorerOptions.ReleaseEarly`, with `--release`), the release may also come while the link is still being set up (AwaitingConnection, AwaitingV22Connection), not only on an established link, under the same delivery gate. Figures C4.2 and C4.6 draw a Save (Requeue) for DL-DISCONNECT Request there; codegen emits it and the reference interpreter honours it, but the explorer does not route through saves yet (packet-net/ax25sdl#97), so here the request still goes to the page's upper-layer catch-all and is dropped; the rows say so rather than modelling the Requeue;
- with `--reconnect A|both` (`ExplorerOptions.Reconnect`), `DL_CONNECT_request` from that station's layer 3 (or either's), once, on a live or waiting link (AwaitingConnection, AwaitingV22Connection, Connected or TimerRecovery), once every frame either station submitted has been delivered upward at its peer (the release's gate). The layer 3 then waits for the answer, `DL_CONNECT_confirm` or `DL_DISCONNECT_indication`, and no state counts as quiescent while it waits (the reconnect answer rule, pinned semantic 13). Not a fault, not work in flight. Table-driven peer only;
- with `--accept-give-up` (`ExplorerOptions.AcceptGiveUp`), no new move but a wider quiescence, the give-up rule: see the Quiescence invariant below and pinned semantic 12;
- with `--local-busy A|B|both` (`ExplorerOptions.LocalBusy`, coverage batch 4), a local busy condition at that station (or either): entered once on an established link (Connected or TimerRecovery) while own receiver busy is clear, left whenever it still holds. It is what §6.4.10 calls a TNC entering a busy condition, and the moves do what the figures draw for DL-FLOW-OFF and DL-FLOW-ON Request once #43 and H3 are fixed (ax25spec PR #109): entering sets own receiver busy and sends RNR response F = 0 with N(r) = V(r), clearing Acknowledge Pending; leaving clears own receiver busy and sends RR command P = 0 with N(r) = V(r), clearing Acknowledge Pending, and when T1 is not running stops T3 and starts T1. No table row runs (the step log reports `pinned:local_busy_enter` / `_leave`), because on today's tables nothing else ever sets own receiver busy (#43). By default the busy period is short: while a station is busy, its peer's T1 does not fire in TimerRecovery once RC has reached N2 - 1, so the busy station leaves its condition while its peer still has a retry for the poll that finds it cleared (every RNR-answered poll costs the peer a retry, see H5). `--long-busy` (`ExplorerOptions.LongBusy`) lifts that hold. Neither move is a fault or work in flight; table-driven peer only (pinned semantic 14);
- with `--t3` (`ExplorerOptions.T3`, coverage batch 4), `T3_expiry` at a station whose T3 is running, on a page with a T3 arm (figc4.4 only; figc4.5 has none, #91), under the quiescent-timeout rule T1 uses and only while no T1 runs at either station. The station's own half follows from the figures, which stop T3 whenever they start T1. The peer's half is a modelling assumption, not physics: it assumes T3 outlasts the peer's whole retry loop (N2 x T1), whereas §6.7.1.3 only requires T3 > T1 ("T3 should be greater than T1"). With the rule loosened to the station's own T1, `gu-v22` with `--t3` has B's keepalive poll a station still in AwaitingV22Connection (which ignores the poll) and give up after N2 polls with no loss behind them (a deadlock at 345 states); the assumption is what keeps such a row about the connect rather than about T3's length. It is a timer, so the timer-free check leaves it out like T1. Two rules come with it (pinned semantic 15): the keepalive rule at rest, and the stricter settled state of the give-up rule;
- with `--unit-data A|B|both` (`ExplorerOptions.UnitData`, coverage batch 5), `DL_UNIT_DATA_request` from that station's layer 3 (or either's), once, in any state: every Data Link page has an arm for it, and UI is the connectionless service, so layer 3 may send it whether a link is up or not. The datagram is labelled `ua0` (A) or `ub0` (B), and the UI frame carries the label. It is a layer-3 decision, not work in flight, so it does not hold back T1, which is what lets a datagram arrive in Timer Recovery or Awaiting Release. With `--ui-form` (`ExplorerOptions.UiForm`) the datagram takes another form: `poll` (a UI command with P = 1) and `response` (a UI response, F = 0) are put on the air by the harness, as from another implementation (the step log reports `pinned:ui_poll` / `pinned:ui_response`), because DL-UNIT-DATA Request carries no P bit and the figures send only UI commands with P = 0; `long` goes through the sender's arm and fails the receiver's N1 check (`info_field_length_le_N1_and_content_is_octet_aligned` is false for a UI frame). Not a fault; table-driven peer only (pinned semantic 16);
- with `--frame-errors LIST` (`ExplorerOptions.FrameErrors`, coverage batch 6), a channel fault under the budget: the head frame arrives corrupted, in each listed form that applies to it, and the receiver sees the frame-error input the figures draw instead of the frame. `control` (any frame) raises `control_field_error`, `info` (an S or U frame that may not carry an information field: not I, UI or FRMR) `info_not_permitted_in_frame`, `length` (an S or U frame other than UI) `u_or_s_frame_length_error`; `n1` and `i-response` hit an I frame reaching a station in Connected or TimerRecovery (the pages with an I frame input), which then sees `I_received` with the N1 atom false or with the command bit lost. A page without the arm takes a frame-error input on its lower-layer catch-all. Rules and judgement calls: pinned semantic 17;
- with `--inject A|B|both` and `--inject-frame FORM` (`ExplorerOptions.Inject`, `InjectedFrame`, coverage batch 6), the station puts one frame on the air, once, as from another implementation (the step log reports `pinned:inject_*`): `rej-poll` (a REJ command with P = 1, while the receiver is in TimerRecovery), `srej-command` and `srej-poll` (an SREJ command with P = 0 or 1, while the receiver is in Connected or TimerRecovery), each with N(r) = the sender's V(r) and only while that names a frame outstanding at the receiver; `ua-f0` (a UA response with F = 0, while the receiver waits in AwaitingConnection, AwaitingV22Connection or AwaitingRelease); `frmr` (an FRMR response, while the receiver is in Connected or TimerRecovery). From coverage batch 7, with `RejMayEqualVs` (`--rej-may-equal-vs`) the rejects may also name the receiver's V(s) (nothing outstanding), only while the receiver is in TimerRecovery with both channels empty, and for an SREJ only with V(a) = V(s) (it does not move V(a), so otherwise it asks for a frame never sent). Also from coverage batch 7, the injected I commands, each carrying its own payload label (`xa0`, `xb0`, and `xa1` for a second injection) and N(r) = the sender's V(r), while both stations are in Connected or TimerRecovery and no I frame is on the channel to the receiver: `i-frame` and `i-poll` (P = 0 or 1, N(s) = the receiver's V(r), only when that is the sender's V(s), the sender's queue is empty and everything either station submitted has been delivered), `i-poll-ahead` (P = 1, N(s) = V(r) + 1; not naming the sender's V(s) through the REJ it draws unless the sender is in TimerRecovery with both channels empty) and `i-poll-stale` (P = 1, N(s) = V(r) - 1, outside the window). The out-of-sequence forms are for links without SREJ. `--inject-frame FIRST,SECOND` puts a second frame on the air after the first (`ExplorerOptions.InjectedThen`). No table sends any of these forms. Pinned semantic 18. `--fired` lists the table rows a search fired.

**Data submission.** All frames are submitted up front: the seeded state has every `DL_DATA_request` already applied, so the queues start full (labels `a0..`, `b0..`). This loses interleavings where data arrives after recovery has begun. The exception is `--data-after-confirm` (`ExplorerOptions.DataAfterConfirm`) on the disconnected seed: then nothing is submitted in the seed, and each station's layer 3 submits its frames by moves once its link is up, as a well-behaved layer 3 would. B may have data in that case. Layer 3 follows what its data link tells it (pinned semantic 13): it stops on `DL_DISCONNECT_indication` or `DL_DISCONNECT_confirm` and resumes after the next `DL_CONNECT_confirm` or `DL_CONNECT_indication`; a DL-ERROR or a re-establishment the data link started itself does not stop it, because layer 3 still believes the link is up (figc4.2 keeps that data while Layer 3 Initiated is clear). It never offers a frame twice: what it had offered before the link went down, and the data link then discarded, stays offered and undelivered, so a scenario that loses it can never be clean. Until coverage batch 3 the link-up flag never cleared, so after a disconnect layer 3 submitted `DL_DATA_request` to a station in Disconnected, which both tools reported as a MachineError (`l3-down-mod128` was one at 15 steps); the stop rule and the routing of upper-layer primitives to their catch-all (pinned semantic 5) removed it. With `--data-before-confirm`, A's layer 3 starts out treating the link as up.

**Seeds.** `connected`: both stations Connected with zeroed variables, T3 running, modulo 8, k (default 4, 1..7), SREJ on or off (SREJ implies version 2.2 on both), N2 (default 4). `disconnected`: both Disconnected, A has issued `DL_CONNECT_request` (with `--mod128`, A is seeded at modulo 128 so that sends SABME) and then submitted its data (figc4.2 discards data offered while layer 3 initiated, as the July 1998 edition of the figure labels it, with no indication to layer 3: ax25spec#161), or, with `--data-after-confirm`, holds it until the link is up; `--peer-declines-sabme` makes the table-driven B answer SABME with DM while accepting SABM (`able_to_establish` = false for SABME). `awaiting-v22`: A is already in AwaitingV22Connection with its SABME P=1 in flight (RC 1, layer 3 initiated, T1 running, modulo 128, version 2.2: the initial state of the golden trace `frmr-fallback-downgrades-to-sabm`, plus the frame that put it there), B Disconnected, no data. It exists because on the current tables a cold `DL_CONNECT_request` never reaches figc4.6 (#44 routes the SABME initiator to figc4.2), so the figc4.6 columns that #45 and #48 live in are unreachable from the `disconnected` seed; this seed enters them directly, as #44's fix would.

**Station B as a v2.0 stub peer** (`--peer v20-frmr|v20-dm`, connect-phase seeds only). A hand-written model of an October 1984 AX.25 v2.0 station, not a table-driven machine: the v2.2 figures cannot play a peer that does not know SABME. It answers SABME with FRMR (`v20-frmr`, the figc4.6 t14 trigger) or with DM F=1 (`v20-dm`, the #48 case), accepts SABM with UA and is then "connected, modulo 8", answers a polled supervisory command with RR F=1, and ignores responses. It has no data phase: both frame counts must be 0 and the scenario ends at "link established with modulo 8", which is the stub's quiescent condition. That was the smaller of the two options the brief allowed (the other being a minimal RR-acknowledging data phase) and it is enough because every defect under test is in the connect phase. Its rules are pinned semantic 10 below, with the 1984 citations. It is the environment: no invariant is checked on it, and a frame outside its rule set (an I frame) is a machine error rather than something silently absorbed. No fixed tables exist to discriminate #45 or #48 against; the control cases are the same stub with a v2.0 (modulo 8) initiator, which connects with SABM, UA and no timer, and a table-driven v2.2 peer answering the seeded SABME with UA.

**Bounds.** Frames per direction 0..3 in the grids (the code takes any non-negative count; the fault-free #54 rows use 9), budget 0..3, k 1..7, N2 2..4, flow-control rounds (default 1), a depth cap (default 80) and a visited-state cap (default 400 000). Sizes on the current tables: 3+3 frames with budget 1 is about 51 000 states in 2.4 s; 3+3 with budget 2 is about 600 000 states in 20 s; flow control at one station roughly triples a cell (the largest cell above passes 1.2 million); the connect-phase cells against the stub peer are under 110 states; every calibration case runs well under a second.

## Invariants

Each is individually switchable (`--disable ...`) so the calibration suite can say which one fires.

- **Defined state**: both stations are in a state the tables define.
- **Sequence sanity** (ported from packet.net's `InvariantChecker`): V(s)/V(a)/V(r) in range, outstanding frames (V(s) minus V(a), mod 8) never exceed k, and the SREJ exception count never exceeds k (each outstanding SREJ names a distinct missing frame inside the window, so a coherent receiver has at most k-1; the bound turns the #42 runaway, whose count is unbounded, into a verdict instead of a depth-bound hit).
- **Delivery** (ported from `InvariantChecker`): the sequence of payload labels each station delivered upward is an exact in-order prefix of what the peer submitted: no gap, no duplicate, no reorder. `DL_DATA_indication` carries the delivered label, which is how order is observed.
- **Reject coherence** (ax25spec#40 stated exactly, generalised). Emitter side: when a station emits REJ or SREJ with N(r) = x, x must be a frame it has not received in sequence (x = V(r), or a not-yet-held frame inside its receive window). Receiver side: when the peer receives that REJ/SREJ, x must be inside the peer's outstanding set [V(a), V(s)). The report says which side failed. The receiver-side check is strict for REJ too: the brief's option of accepting REJ with N(r) = V(s) as a pure acknowledgement is available as `--rej-may-equal-vs` but off by default, because on a FIFO channel a REJ can only carry the receiver's V(r) at a moment when it had already received a frame above V(r), so the sender had sent frame N(r) and V(s) > N(r) ever since; N(r) = V(s) can only come from a reject raised on a stale duplicate (the #40 class), and figc4.7's `Invoke_Retransmission` is a do-while that then pushes I(V(s)), a frame that was never sent.
- **Acknowledgement coherence**: a station's V(a) never advances past the number of frames the peer has delivered upward. Absolute (unwrapped) counters are tracked per direction alongside the modulo values, so this is exact; a link (re)establishment zeroes the variables without acknowledging anything and is excluded from the count.
- **Flow-off delivery** (`flow-off-delivery`): no `DL_DATA_indication` is delivered at a station while its layer 3 has flow off (after its `DL_FLOW_OFF_request`, before its `DL_FLOW_ON_request`), nor, with `--local-busy`, while its own receiver is busy (§6.4.2.2: a busy TNC "ignores any received I frames"). This is what DL-FLOW-OFF is for: once the busy condition is up, figc4.4's own `I frame received / own receiver busy? yes` arm discards the frame, so a correct figure never delivers while flow is off, even for a frame that was already on the air.
- **Busy tracks flow** (`busy-tracks-flow`, the cheaper check): after `DL_FLOW_OFF_request` the station's own-receiver-busy condition is set, and after `DL_FLOW_ON_request` it is clear. §6.4.10 ("Whenever a TNC enters a busy condition, it indicates this by sending an RNR response") is what DL-FLOW-OFF exists to trigger, and the figure's own DL-FLOW-ON arm assumes it: it only acts when busy is set.
- **Peer-busy hold** (`peer-busy-hold`, coverage batch 4): a station that has received RNR from its peer sends no I frame until it receives RR, REJ, SREJ, or a frame that resets or ends the link (SABM, SABME, UA, DM, DISC, FRMR). §6.4.9: "Whenever a TNC receives an RNR frame, it stops transmitting I frames until the busy condition is cleared." It is checked on the frames sent and the frames received, not on the station's peer-busy flag, so a figure that ignores an RNR is caught (`seeded-rnr-ignored`). Only an RNR raises it, and on today's tables only `--local-busy` produces one.
- **Busy indication** (`busy-indication`, coverage batch 4, with `--local-busy` only): a station whose own receiver is busy sends RNR, never RR, REJ or SREJ (§6.4.10: "If a received S frame has the P bit set to 1, the TNC sends an RNR frame with the F bit set to 1"). `seeded-busy-says-rr` shows it firing.
- **UI handling** (`unit-data`, coverage batch 5, with `--unit-data` only), checked on every UI frame a station receives, whatever event the page dispatches it as: a page that has lost its UI arm sends the frame to a catch-all, and the check still judges what came of it (`seeded-ui-arm-deleted`; before the review of this batch the check keyed on the `UI_received` event, so deleting a page's UI arms went unnoticed). Delivery is UI Check's (figc4.7): a UI command whose information field passes the N1 check is delivered upward exactly once, as `DL_UNIT_DATA_indication` carrying the sender's datagram label, and nothing else is; a UI response is not delivered and draws DL-ERROR (Q); a UI command that fails the N1 check is not delivered and draws DL-ERROR (K). The answer is §4.3.3.6's ("A received UI frame with the P bit set causes a response to be transmitted. This response is a DM frame when in the disconnected state, or an RR (or RNR, if appropriate) frame in the information transfer state"): a UI command with P = 1 is answered by exactly one response with F = 1, DM outside Connected and TimerRecovery and RR or RNR in them; a UI command with P = 0 by nothing. §4.3.3.6 names only the disconnected state for the DM; that a poll gets DM in AwaitingConnection, AwaitingV22Connection and AwaitingRelease too comes from the figures' own other pages (figc4.2 and figc4.3 draw DM F=1 there), not from the prose, and `ui-cold-poll` is exactly that case. For an oversize UI the check follows the figure: UI Check draws DL-ERROR (K), while the error list gives K as unexpected frame and R as "UI frame exceeded maximum allowed length"; `ui-long` takes K, and the mismatch is recorded on ax25spec#154. What a station sends on a UI response is not judged. Whether the datagram is too long and which label it must carry come from the scenario, not from the frame or the atom the harness supplied, so harness plumbing that lost either is caught too. Five seeded fixtures show it (and the rest rule below) firing (`seeded-ui-*`).
- **Frame errors** (`frame-error`, coverage batch 6, with `--frame-errors` only): a station that receives a corrupted frame reports it to layer 3 with the DL-ERROR Indication the figures draw for the form, (L), (M) or (N) for the three frame-error inputs and (O) for an I frame that fails the N1 check or arrives as a response, and delivers nothing upward. It is keyed on the corruption, not on the event the page dispatches it as, so a page whose frame-error arm is deleted (the input falling to a catch-all) is caught (`seeded-fe-arms-deleted`). For the I response the check follows the figures, which draw (O) in figc4.4 and figc4.5; the Data Link error list in Appendix C4 gives (S), "I response received", and the July 1998 figc4.5 draws (S) (see the observation under the novel findings).
- **Quiescence under a fair channel** (liveness, on the reachable-state graph): after the BFS, from every reachable state a fault-free path must lead to a quiescent state (both Connected, both channels and queues empty, V(s) = V(a) on both, all submitted data delivered, no owed confirms). Implemented as reverse reachability from the quiescent states over the non-fault edges of the whole graph ("the channel eventually stops faulting"); a state that cannot reach quiescence is reported with the path to it and its enabled moves. That is "no unclearable exception" and "livelock" as a graph property instead of a timeout. With the give-up rule (`--accept-give-up`, off by default) a link that ran out of retries for a reason the faults explain is at rest too: a station that exhausts N2 (a T1 expiry that takes it to Disconnected) has given up honestly when at least as many frames were dropped since that station last made progress as its retry loop has attempts, and a settled honest give-up (some station gave up honestly and none unjustifiably, each station Disconnected or at rest as above, nothing in flight or owed) with everything delivered is quiescent. One that lost data is not: a deadlock there is reported as **give-up loss** (`GiveUpLoss`), so the loss is visible as such rather than accepted. An unjustified give-up never rests: with the rule on, no state counts as quiescent once a station has given up without the losses to justify it, so #9, whose give-up comes after the acknowledgements progressed, stays a deadlock. With `--unit-data`, every UI datagram must have been sent and then either reached its peer or been dropped by the channel (pinned semantic 16). With `--frame-errors`, the reset rule (pinned semantic 17): no state rests after a reset no corrupted frame justifies, and a deadlock in a settled honest reset that lost data, with the layer 3 of every station that lost data told, is reported as **reset loss** (`ResetLoss`), the frame-error counterpart of give-up loss. With `--t3`, two more conditions (pinned semantic 15): at rest a Connected station has T1 or T3 running (the keepalive rule), and the give-up rule's settled state needs every station Disconnected (a station left up is not settled: its keepalive will find the peer gone). The cheaper **deadlock** check (a terminal, non-quiescent state) runs first and is sound even when a bound was hit. With the v2.0 stub as B, "B at rest" is just "the stub is connected". The state reported for a liveness failure is the shallowest one that cannot reach quiescence and has no non-fault edge (non-T1 too, for the timer-free check) to any other state, i.e. where the model is actually stuck; the seed is usually non-reaching as well, but the stuck state is the one that reads as a counterexample.
- **Timer-free progress** (off by default, `--selective-progress`): quiescence must be reachable without any `T1_expiry` move. In the data phase this is selective-recovery progress: with SREJ negotiated and a fault-free future, a loss is recovered without a timeout; it is only meaningful there with `--drop-scope interior-i` and drops only (losing a trailing frame, an SREJ or an acknowledgement can only be recovered by T1). It holds on the current tables for an interior loss with 2 frames; it never gets to run on #42 (see the score). In the connect phase, against the v2.0 stub peer with no faults, the same check reads as "the v2.0 fallback re-establishes without a timeout": a FRMR (or DM) to our SABME should be answered by a SABM straight away, and a connect that only comes up because figc4.2's T1 retry happens to send SABM has not fallen back at all. That is the check that sees #45 (and #44 masking it); it now has discriminating calibration cases.
- **Machine error** (always on): the interpreter threw. Either an unbound verb/atom, a non-deterministic table, a state page with no arm (direct or catch-all) for a received frame, or a pinned-semantics gap such as a retransmission of a frame the station never sent.

## Pinned delegated semantics

The figures delegate some behaviour to "the implementation". Every choice the explorer or the interpreter makes in those gaps is listed here, with the citation that settles it or a note that it is a judgement call. Ask of every counterexample: does it depend on one of these?

1. **Retransmission** (`Machine.cs`, `RetransmitOldFrame`; `QueueEntry`; `RetainedFrames`). `Invoke_Retransmission` (figc4.7) backtracks V(s) to N(r) and loops "Push Old I Frame onto Queue" until V(s) returns to X; the figc4.4/4.5 SREJ arms do "Push Old I Frame N(r) on Queue". The #75 interpreter models these as re-queueing and restores V(s), so a re-pop through the table's fresh-frame path would renumber the frames from V(s) (its ambiguity #1) and loss recovery could never complete. Pinned the way every real implementation does it: the station retains a copy of every I frame it has sent, keyed by N(s), from V(a) upward (pruned to [V(a), V(s)) after each dispatch); the two push verbs re-queue an entry carrying the original N(s) and the retained payload; when such an entry pops in Connected or TimerRecovery it is re-emitted with its original N(s), the current V(r) as N(r) and P = 0, V(s) is untouched, the window-full pop check does not apply (the frame is already inside the window), Acknowledge Pending clears (the frame carries an acknowledgement) and, mirroring the fresh-frame pop, T1 starts (stopping T3) if it is not already running. The reported transition id is `pinned:retransmit_old_i_frame`. Citations: packet.net `src/Packet.Ax25/Session/ActionDispatcher.cs` (`PushOldIFrameOntoQueue` maps to `EmitOldIFrame(tx, ctx.VS)`, `PushOldIFrameNrOnQueue` to `EmitOldIFrame(tx, N(r))`, both emitting directly with the original N(s)); direwolf `src/ax25_link.c` `resend_for_srej` and the `invoke_retransmission` loop; prose §6.4.7 and §6.4.8 ("retransmits the I frames"). Two consequences are deliberate: a re-queued frame the station holds no copy of (never sent, or already acknowledged) is an interpreter error at the pop, not a silently skipped frame (packet.net skips it via `IsOutstanding`; that sender-side guard is exactly what the brief says absorbed the #40 symptom, so the model refuses to have it); and a frame that is re-queued twice (a duplicated REJ, say) is sent twice, as the figure says. The existing golden traces assert the re-queue effects and queue labels, which are unchanged. **Peer busy** (coverage batch 4): while the station's peer receiver busy is set, a re-queued old frame takes the table's own pop arm instead (`t03_i_frame_pops_off_queue_yes`, "Push I Frame on I Queue"), which pushes it back, so nothing is retransmitted to a busy peer; the figures draw exactly that, and §6.4.9 says a station that receives RNR "stops transmitting I frames until the busy condition is cleared". Before batch 4 the retransmission bypassed the peer-busy check too; no earlier row ever had a busy peer, so nothing changed for them.
2. **Link multiplexer.** `LM_seize_request` is answered by the local multiplexer with `LM_SEIZE_confirm` to the same station; it is not a peer frame. Modelled as a boolean "owed" flag per station (a second request before the confirm is idempotent; the figure's own `ack_pending` flag already collapses them). `LM_release_request` and `LM_data_request` are no-ops. When the station's current page has no `LM_SEIZE_confirm` arm (after a reset) the confirm is routed to `all_other_primitives__from_lower_layer`. Judgement call, consistent with C4.2's description of the primitives.
3. **Interpreter policies adopted from #75** (see `docs/golden-traces.md`): transition guards evaluate against the pre-transition state, subroutine path guards and loop predicates live; P/F/N(s)/N(r) staging registers reset per dispatch and an emission without staged N(r)/N(s) is an error; the I-frame queue is a FIFO, `DL_DATA_request` joins the tail, pushed-back and re-queued frames enter at the head preserving order; `Check_I_Frame_Acknowledged` is exactly the figc4.7 subroutine table (no extra semantics); "Save Contents of I Frame" stores the frame in the receive buffer keyed by N(s) and "Discard Contents of I Frame" is a no-op, so on the SREJ-enabled REJ arm (figc4.4 `..._no_yes_no_yes`, which draws Save then Discard) the saved copy stays in the buffer and is drained later; the environment atoms default to true; subroutine call labels bind through the explicit alias map.
4. **`DL_DATA_indication` carries the delivered frame's payload label** (`UpperEffect.Detail`), for the arriving frame on the in-sequence arm and for the retrieved frame inside the drain loop ("Retrieve Stored V(r) I Frame" sets the label the next indication carries).
5. **Catch-all arms.** A frame whose `*_received` event has no arm on the current page is delivered as that page's catch-all: `all_other_commands` (Disconnected, commands), `i_or_s_command_received` (AwaitingRelease), `all_other_primitives__from_lower_layer` (the Awaiting* pages, responses). An upper-layer primitive (`DL_DATA_request`, `DL_CONNECT_request`, `DL_DISCONNECT_request`, the seed's injections included) with no arm on the page goes to its `all_other_primitives__from_upper_layer` catch-all, which every Data Link page has and none acts on (coverage batch 3; before it, only frames were routed and such a primitive was a machine error). A page with neither is a machine error. Judgement call from the figures' own "all other" columns. One consequence is recorded rather than modelled: figc4.2 and figc4.6 draw a Save (Requeue) for DL-DISCONNECT Request, which the explorer does not route through yet (the tables carry it and the interpreter honours it, pinned semantic 19; the explorer part of packet-net/ax25sdl#97 is still open), so here that request reaches the catch-all and is lost; `release-early-*` show it.
6. **The channel** is a FIFO per direction; a duplicate is a copy left at the head, so it arrives immediately after the original; reordering (swap the first two) exists but is off by default because a single AX.25 channel does not reorder and the figures' N(r) validity checks presuppose order. Judgement call; the calibration scenarios use drop and dup only, except the `ro-*` rows of coverage batch 2, which reorder to reach the N(r)-error arms (ax25spec#95 is the verification item for reordering). Reject coherence presupposes a FIFO channel (a reordered reject can legitimately name a frame already acknowledged), so the reorder rows that reorder rejects run with it off.
7. **Quiescence requires Connected.** A station in TimerRecovery with everything acknowledged is not quiescent, following §4.4.5.1 ("the timeout condition is cleared by the reception of an acknowledgement for the sent frame(s)"). `--quiescence-accepts-timer-recovery` is a triage aid that relaxes this so a grid run can look past hypothesis H1.
8. **Timers are symbolic** (running/stopped/expired only), so anything numeric (T1 value, SRT, Karn sampling) is out of the model's reach.
9. **Version flags.** `version_2_2` is seeded equal to `--srej` (a link using SREJ has negotiated v2.2, §4.3.2.4 and §6.3.2); modulo is 8 on both sides except A under `--mod128` on the `disconnected` seed (set by hand, since the tables never set it; with `--data-after-confirm` this reaches the data phase too) and the `awaiting-v22` seed (A at modulo 128 with version 2.2 set). The tables themselves never assign the modulus (#54: the figc4.7 `Set_Version_2_0` / `Set_Version_2_2` subroutines, which would, are never invoked; the pages call the flag verbs), so an A that falls back to v2.0 keeps modulo 128 in this model, and a B that accepts SABME keeps modulo 8. Within 8 frames that has no wire effect the abstract frame model can see; past the wrap it does (the #54 row of the calibration table).
10. **The v2.0 stub peer** (`V20Peer.cs`). Each rule cites the October 1984 text in `spec-sdl/v2.0/` (a scan; read page by page). SABME is a control field a v2.0 station does not know: `v20-frmr` answers FRMR with F = P under §2.3.4.3.3.1 ("The FRMR response frame is sent to report that the receiver of a frame cannot successfully process that frame ... 1. The reception of an invalid or not implemented command or response frame", where "an invalid or not implemented command or response is defined as a frame with a control field that is unknown to the receiver"); that is the trigger figc4.6 t14 is drawn for (v2.2 §4.3.3.9 "FRMR is retained for compatibility with older versions", §6.3.2 "a version 2.0 connection is made", §6.5). `v20-dm` answers DM with F = 1 under §2.3.4.3.5 ("While a DXE is in the disconnected mode, it will respond to any command other than a SABM or UI frame with a DM response with the P/F bit set to 1") and §2.4.3.4.3; both readings are legal v2.0 behaviour, and XRouter takes the DM one on the wire (#48). SABM is accepted with UA F = P (§2.3.4.3.4 "The UA response frame is sent to acknowledge the reception and acceptance of a SABM or DISC command frame", §2.4.3.4.2) and the stub is then connected at modulo 8. DISC: UA F = P when connected, DM F = 1 when not (§2.4.3.4.1). Any other command while disconnected: DM F = 1 (§2.3.4.3.5). A supervisory command with P = 1 while connected: RR F = 1, N(r) = 0 (§2.4.2); with P = 0 nothing (no T2 delayed acknowledgement). UI frames and all responses are ignored. No timers, no unsolicited frames, no data phase (an I frame is a machine error; the seeds enforce zero frames). The one judgement call is F = P rather than F = 1 on the FRMR (§2.3.4.3.3 does not say; figc4.6 t14 has no F guard so it cannot matter here); v2.2 §4.3.3.5 is the same DM rule in the current prose.
11. **Layer-3 flow control** is a scenario input, not a peer frame: the moves are described under the model. The round bound and the delivered-frames threshold are judgement calls that keep the space finite and put the FLOW_OFF where it can be observed (after at least one delivery, so the next delivery is the test). Layer 3 is assumed to flow-control only an established link (the moves need a direct arm on the page).
12. **The give-up rule** (`--accept-give-up`, `ExplorerOptions.AcceptGiveUp`; TLA+ constant `AcceptGiveUp`). A give-up is a T1 expiry that takes a station to Disconnected: the RC = N2 arms of figc4.2, figc4.6, figc4.3 (Awaiting Release) and figc4.5. It is honest when the drops since the station's last progress reach the attempts its retry loop has before it gives up. The attempts are read off the figures, not chosen: `Establish_Data_Link` sets RC := 1, so figc4.2 and figc4.6 give up after N2 transmissions (threshold N2); DL-DISCONNECT sets RC := 0, and Connected's T1 expiry sets RC := 1 only after a first loss, so Awaiting Release and Timer Recovery give up after N2 + 1 (threshold N2 + 1). Judgement calls, each chosen so the rule errs towards refusing a give-up: only drops count as losses (a duplicate or a reorder loses nothing); a drop on either channel counts for both stations (lenient, but bounded by the next point); progress, which clears a station's count, is its own frames being acknowledged further (the acknowledgement counter of the ack-coherence check advancing) or its layer 3 being told the link came up (DL-CONNECT confirm or indication), and it is deliberately not RC, which is what #9 gets wrong. A station left Connected with nothing queued or outstanding after its peer gave up counts as settled only if nothing its peer sent at or after the give-up reached it: such a station never heard the give-up (its DM was lost, or there was none), and on the air its T3 would probe and find the peer gone, which the model cannot show because T3 is outside it. A station that received the DM and stayed up is not settled, so a figure that ignores the DM is still caught (`seeded-dm-ignored`). Since T1 only fires with both channels empty, every frame that reaches a station after its peer gave up was sent at or after the give-up, so the harness only has to note that one arrived. The loss count is not reset when a retry loop starts: drops from before the loop (on either channel, since the station's last progress) count towards it too. That could let a give-up through whose own loop lost fewer frames than it has attempts, for instance a #9-like early give-up that follows an unacknowledged loss earlier in the exchange; the rule accepts that leniency rather than define where a loop starts independently of the figures' RC. The thresholds for Awaiting Release and Timer Recovery (N2 + 1) are not pinned by a row: on the current tables no give-up there comes before N2 + 1 failed attempts, so lowering them to N2 changes no verdict; only a defective table could tell them apart. Data lost in an honest give-up is the protocol doing what it says (DL-ERROR and DL-DISCONNECT reach layer 3), but accepting it would also accept a defect that loses data on the way down, so it is reported, under its own name. Without the rule, a release rest does not ask how the link went down: an Awaiting Release give-up after all data was delivered passes as released whether or not the faults justify it, so a release scenario whose budget reaches N2 + 1 should turn the rule on.

13. **Layer 3** (coverage batch 3). Layer 3 is the scenario, not a peer, and it is well-behaved: it submits data only while its data link says the link is up (with `--data-after-confirm`), stops on `DL_DISCONNECT_indication` or `DL_DISCONNECT_confirm`, resumes after the next `DL_CONNECT_confirm` or `DL_CONNECT_indication`, and never offers a frame twice, so data the data link discarded stays visible as undelivered instead of being dropped from the count. A layer 3 that issues `DL_CONNECT_request` on a live or waiting link (`--reconnect`) expects an answer: `DL_CONNECT_confirm` (C4.2's response to a DL-CONNECT Request) or `DL_DISCONNECT_indication` (the attempt failed); a DL-ERROR or a `DL_CONNECT_indication` alone is not an answer, and until one comes no state is quiescent, plain, released or a settled give-up. More generally, every layer 3 keeps the last link report its data link gave it (up: `DL_CONNECT_confirm` or `_indication`; down: `DL_DISCONNECT_indication` or `_confirm`), and at rest that report must match the station's state: up only while Connected or TimerRecovery, down only while Disconnected (no report yet constrains nothing). So a disconnect indication answers a reconnect only if the station really rests Disconnected, and a layer 3 told the opposite of what its station did is never at rest (the report rule, from the review of this batch, which found that a DL_DISCONNECT_indication in place of the connect confirm was accepted; `seeded-confirm-as-disconnect` pins it). One leniency is known and accepted: figc4.2 `t04_ua_received_yes_no_no` emits DL_CONNECT_confirm with Layer 3 Initiated clear (a link reset by the data link itself, with V(s) != V(a)), so if a reconnect were followed by such a reset before its own UA, that confirm would count as the answer; layer 3 cannot tell one confirm from another, and no current row takes that path. The reconnect and the early release use the release's gate (everything both sides submitted is delivered: the application has finished its exchange), and both are limited to a live or waiting link (not Disconnected, where a DL-CONNECT is the ordinary connect, and not AwaitingRelease, where neither the reset nor the release is a live request). Judgement calls: the gate keeps a reset from discarding queued data by design, which would only report the designed loss; the answer rule is what makes `reconnect-tr` a violation (without it both ends end up Connected with everything delivered), and `seeded-reconnect-swallowed` shows both tools enforce it. The rule was checked by removing it in both tools: that seeded row and `reconnect-tr` both became clean. Two implementation notes: the report rule is always on (it adds a field to the state, which changed the state counts of three batch 3 rows and of no earlier row), and both tools set the pending flag after the reconnect's own dispatch, so an arm that answered within that dispatch would be overwritten; no current arm does (each sends SABM(E) or nothing).

14. **The local busy condition** (`--local-busy`, coverage batch 4). The figures enter the busy condition only through DL-FLOW-OFF Request, whose busy arm is on the wrong branch (#43) and emits RNR with no N(r) staged (H3), so on today's tables no station ever becomes busy and the whole peer-busy family is unreachable. §6.4.10 speaks of "a TNC" entering a busy condition, which is wider than layer 3 asking for it, so the harness injects one, with the action stacks the corrected figure (ax25spec PR #109) draws for DL-FLOW-OFF and DL-FLOW-ON Request: the RNR and RR carry N(r) = V(r) like every other RR/RNR the figures stage, and leaving starts T1 when it is not running, as figc4.4/4.5 t06 draw. It is an injected stimulus, not a table row, and it changes no table: everything that follows (the RNR at the peer, its polls, the busy station's RNR answers and its discarded I frames, the clearing RR) is the tables. The own-busy arms reached this way are the tables' own; the DL-FLOW-OFF and DL-FLOW-ON busy arms themselves (`t05_dl_flow_off_request_yes`, `t06_dl_flow_on_request_yes_*` on both pages) still hit H3 if layer 3 issues them during a busy period (`h3-busy-flow-off`). Judgement calls: one busy period per station (so the space stays finite); entering only from Connected or TimerRecovery; and, unless `--long-busy`, a short busy period: the peer's T1 does not fire in TimerRecovery once its RC has reached N2 - 1 while the station is busy, which leaves the peer one retry for the poll that finds the condition cleared. Without that hold every busy scenario ends in the H5 teardown, which `busy-b-long` shows on its own.
15. **T3** (`--t3`, coverage batch 4). T3 expires only under the quiescent-timeout rule and while no T1 runs at either station. That no T1 runs at the station itself is the figures' own rule (they stop T3 whenever they start T1); that none runs at the peer is a modelling assumption: it assumes T3 outlasts the peer's whole retry loop (N2 x T1), where §6.7.1.3 only requires T3 > T1. Loosened to the station's own T1, `gu-v22` with T3 is a deadlock: B's keepalive polls a station still in AwaitingV22Connection and gives up with no loss (see the `--t3` move above). Two rules come with it. The keepalive rule: at rest a Connected station has T1 or T3 running (§4.4.5.2: "When T1 is not running ... T3 periodically causes the TNC to poll the other TNC"), so a link that has lost its keepalive at both ends is not at rest (`seeded-no-keepalive`; on the real tables no reachable rest lacks it). And the give-up rule's leniency is tightened: without T3 a station left Connected after its peer gave up counted as settled if it never heard the give-up, because its T3 would have found the peer gone; with T3 modelled it must actually do so, so the settled state needs both stations Disconnected. `seeded-t3-dead` (no T3 arm) shows the tightening has teeth: clean without it (checked by removing it in both tools), a deadlock with it. A TimerRecovery loop entered by a T3 expiry (figc4.4 t13: RC := 1, then the poll) gives up after N2 polls with no loss behind it, so the give-up rule's threshold for it is N2, not N2 + 1 (`t3-gu`, clean; with N2 + 1 it would be an unjustified give-up). Without `--t3` none of this applies and every earlier row is unchanged.

16. **UI datagrams** (`--unit-data`, coverage batch 5). How UI delivery is counted. UI is unacknowledged: nothing in the protocol recovers a lost UI frame, so a datagram the channel drops under the fault budget is honestly lost and must not be a violation. What can be a violation is the data link's handling of a datagram it was handed or received, and that is checked by two rules, neither of which looks at the channel's luck. (1) At the receiver, per step: every UI frame that arrives is judged then and there (the UI handling check), whatever event the page dispatches it as, so a UI swallowed (by its own arm or, if the page has lost the arm, by a catch-all), delivered twice in one dispatch, delivered with the wrong label, delivered when it should be refused, refused when it should be delivered, or answered wrongly is a violation at the step it happens, whatever the faults did before. A channel duplicate delivers the same datagram twice, in two steps; that is the channel's doing and both deliveries are legitimate (UI has no sequence number to detect a duplicate). (2) At rest: every datagram layer 3 handed down was sent and then either arrived (and was judged by (1)) or was dropped by a fault. So a datagram the sender never put on the air leaves the system short of rest and shows as a deadlock, while a dropped one is accounted for. Together they make a lost or mishandled UI visible without making an honestly lost one a violation. Seeded fixtures: `tables-ui-swallowed`, `tables-ui-arm-deleted` (Timer Recovery's UI arms deleted, so the frame falls to the lower-layer catch-all) and `tables-ui-response-delivered` for the delivery half of (1), `tables-ui-poll-unanswered` for its answer half, `tables-ui-unsent` for (2); removing (2) from `TwoStation.tla` alone makes `seeded-ui-unsent` clean in TLC (a disagreement), and so do removing the drop accounting (`ui-tr`), the answer check (`ui-v22`, `seeded-ui-poll-unanswered`), the N1 atom (`ui-long`) or the UI frame's label (`ui-connected`). Judgement calls: one datagram per station; the move does not hold back T1 (a layer-3 decision, as the release is); a UI poll and a UI response are injected because layer 3 cannot ask for either; and the answer to a UI response is not judged (the tables answer a UI response with F = 1 as if it were a poll: figc4.4 `t18` and figc4.5 `t16` test the P/F bit, not the command bit). **ax25spec#154.** §4.3.3.6 says a UI with P set gets DM in the disconnected state and RR or RNR in the information transfer state; figure C4.7's UI Check delivers a UI command whatever its P bit and draws DL-ERROR (Q) only for a UI response; the Data Link error code list (Appendix C4) gives Q as "UI response received, or UI command with P=1 received". The tables take §4.3.3.6's reading, and so does the check: the page arms answer the poll (DM F=1 on figc4.1, 4.2 and 4.3, Enquiry Response F=1 on figc4.4 and 4.5) and UI Check delivers a UI command with P = 1 rather than reporting Q. The July 1998 edition draws UI Check the same way (printed page 108). Rows that turn on that reading are labelled #154. Two things the check takes from the figures rather than the prose: §4.3.3.6 names only "the disconnected state" for the DM answer, and the check expects DM in AwaitingConnection, AwaitingV22Connection and AwaitingRelease as well because figc4.2 and figc4.3 draw it there (`ui-cold-poll` turns on exactly that); and an oversize UI draws DL-ERROR (K) because UI Check draws K, though the error list has K for an unexpected frame and R for "UI frame exceeded maximum allowed length" (`ui-long` follows the figure; the mismatch is recorded on ax25spec#154). Interpreter change: "UI Command" carries the DL-UNIT-DATA Request's payload label and `DL_UNIT_DATA_indication` the received UI frame's (the TLA+ semantics the same), which changes no golden trace (none sends UI).

17. **Frame errors and the reset rule** (`--frame-errors`, coverage batch 6). A corrupted frame is a channel fault: it uses the budget, the liveness checks never count on it, and the give-up rule counts it as a loss as it counts a drop. The receiver sees only the frame-error input (the corrupted frame is not received as itself, so it neither raises nor lowers the peer-busy hold), and the FrameError check judges what it does with it. The data-state arms for these inputs reset the link (Establish Data Link), discarding the I queue, which is the loss ax25spec#50 and #114 discuss; the rule for that data follows the give-up rule's precedent (pinned semantic 12). A **reset** is a dispatch at a station in Connected or TimerRecovery that sends SABM or SABME, except layer 3's own DL-CONNECT Request (`--reconnect`). It is **honest** when the dispatch is the corrupted frame itself, and unjustified otherwise (a duplicated UA, #114; an N(r) error under reordering; figc4.5's UA arm after #167's reset). With the option on, no state is at rest once a station has reset without justification, whatever was lost; an honest reset that lost nothing may rest (`fe-release`). Each layer 3 keeps how far it has been **told**: a DL-ERROR Indication sets "error reported", and a DL-CONNECT Confirm or Indication after it "told". A deadlock whose stuck state is a settled honest reset (some station reset honestly and none without justification, everything at rest as plain quiescence has it except the delivery count) that lost data, where the layer 3 of every station whose data was lost has been told, is reported as `ResetLoss`, not as a plain deadlock: the figures did what they say, and the loss is visible as such rather than accepted. Data discarded with its layer 3 not told stays a plain deadlock (`fe-tr-b3`, `inj-frmr-a1`: the N1 and FRMR arms clear Layer 3 Initiated, so with V(s) = V(a) the UA brings no confirm), and so does a loss behind an unjustified reset. Seeded fixtures: `tables-frame-error-unreported` and `tables-frame-error-arms-deleted` for the check, `tables-reset-unconfirmed` for "told" (at the station that did not reset and at the one that did), `tables-reset-wrong-code` for the code that tells, `tables-rr-resets` for "honest" (with nothing lost the run is a deadlock, not a rest; with a1 discarded it is a deadlock, not a reset loss). "Told" asks for the DL-ERROR that names the reset's cause, the corrupted frame's own code at the station that received it and (F) "data link reset" at a station that takes its peer's SABM, followed by a connect report; any other DL-ERROR does not count (`seeded-reset-wrong-code`: the peer's (F) replaced by (A) is a deadlock, not a reset loss). Known leniencies, accepted: "told" is a latch, never cleared once set, so after an honest reset a later, unrelated loss that layer 3 is not told of would still classify as a reset loss; and the loss is not tied to particular frames, so a loss with another cause at a station that was also told of an honest reset would be accepted the same way (the give-up rule has the same leniency). Without `--frame-errors` none of this applies and every earlier row is unchanged.
18. **Injected frames** (`--inject`, coverage batch 6). The forms no table sends, put on the air by the harness as from another implementation, in the pattern of the UI poll and response (pinned semantic 16): a REJ command with P = 1, an SREJ command (P = 0 or 1; ax25spec#164, SREJ is a response only), a UA with F = 0 and an FRMR in the data phase. Each is gated on the receiver's page, and the rejects on naming a frame outstanding at the receiver, so a reject coherence verdict is never about the harness's own frame. The gates are judgement calls that aim each form at the columns it exists for. The move is once per station and, like a channel fault, not a move the liveness checks may use (a scenario need not inject to rest); it does not hold back T1. No new rule judges the answers: the existing checks do (busy indication for the REJ poll, ax25spec#171). The injected I frames (coverage batch 7) need one delivery rule. Their payload is not one of the peer's submissions, so it moves no delivery count and is never owed; the Delivery check requires it to be delivered exactly when the receiver accepts that frame in sequence (N(s) = V(r) before it, and V(r) moves past it), once within that dispatch, and reports anything else as a Delivery violation: accepted but not delivered, delivered without V(r) moving, delivered twice in that dispatch, or delivered in any other dispatch (out of sequence, or later from a receive buffer). Seeded: `tables-injected-delivered` and `tables-injected-undelivered`. "Once" is per dispatch: a second in-sequence receipt of the same payload after a reset (the receiver's V(r) back at that number) is accepted again, as it would be from a real peer. The in-sequence forms take a sequence number the sender's machine never used, so the receiver's next acknowledgement carries an N(r) past the sender's V(s), and the sender's N(r) error recovery resets the link: the figures' honest answer to a peer that acknowledges a frame never sent. That is why those forms wait until everything is delivered and the sender's queue is empty: the reset then loses nothing the harness did not cause, and nothing of the sender's own can collide with the injected number. It is also the cheap way to an N(r) beyond V(s) on a FIFO channel (`ip-nr*`); the reject it draws is incoherent by construction, so those rows run with reject coherence off. The out-of-sequence forms are discarded by every arm without SREJ, which is why they are refused with SREJ (the receiver would save the frame under a number the sender may use).

19. **Saves** (packet-net/ax25sdl#97; the interpreter, not yet the explorer). The save mechanics themselves are SDL's, not delegated: a saved input causes nothing, is held in arrival order, and is consumed in the first state entered (the same state included) that does not save it, with an explicit save taking precedence over an "all other" catch-all (AX.25 2.2 C1.2; save: ITU-T Z.101 clause 11.7, whose prose was not checked, semantics as the SDL Forum's Z.100 reference states them; asterisk input and implicit transition: ITU-T Z.103, Z.100 generally; `docs/golden-traces.md`, "Saves"). What the figures and C1.2 leave open is pinned here. (a) **"A new and different state."** C1.2 says a saved input waits "until the state machine ... has reached a new and different state"; SDL attaches the save to each state, so a different state that also saves the input keeps it waiting (figc4.6 t11's DM F = 0 to Awaiting Connection, which saves DL-DISCONNECT Request too: `dl-disconnect-saved-across-v22-fallback`), and re-entering the saving state cannot release it (`dl-disconnect-saved-until-connected`'s SABM retry). The two texts agree on every case the figures can reach. (b) **When.** Held inputs are consumed at the end of the dispatch whose transition entered the state, before any later input: C1.2 makes the transition atomic, and the held inputs arrived before anything still to come. (c) **No arm in the new state.** A released input is handled exactly as a fresh one would be: "in the following state, signal instances that have been saved are treated as normal signal instances". So SDL takes the page's asterisk input (its "all other" column) where it has one and the implicit transition (consume and discard, Z.103) only otherwise. The interpreter does no catch-all routing for any input, so it raises, as it does for a fresh unhandled input; a runtime, or the explorer under pinned semantic 5, routes it to the "all other" column as it would a fresh input. No current table reaches the case. DL-DISCONNECT Request held in Awaiting Connection or Awaiting V2.2 Connection is released into Connected (`t01`, unguarded, to Awaiting Release), Disconnected (`t01`, unguarded), or by a chained replay Awaiting Release (`t01`, unguarded); the two saving states keep it held, and Timer Recovery (which also has `t01`) is not reachable from either. MDL-NEGOTIATE Request and XID Command held in Negotiating are released into Ready, which has `t01_mdl_negotiate_request` (back to Negotiating, where a held XID Command stays held) and `t02_xid_command_received_yes` / `_no` (a P guard that covers both values). (d) **Queue discards.** "Discard Queue", "Discard I Frame Queue" and "Discard Frame Queue" act on the frame queues, not on the input queue, so they leave held inputs alone, and so does a link reset. The spec has no text on held inputs across a reset; Appendix D's ISO 8886 queue model (informative) makes a disconnect "destructive with respect to all objects", which argues against ever losing a DL-DISCONNECT. One consequence will surprise someone: if layer 3 sends DL-DISCONNECT Request and then DL-CONNECT Request while connecting, figc4.2's DL-CONNECT arm (`t07`) leaves the disconnect held, so when UA arrives the link comes up (DL-CONNECT Confirm) and is torn down at once by the held request (DISC, Awaiting Release). That is first-in-first-out and what the figures say. (e) **Stopping.** No Data Link or Management Data Link page draws a stop symbol, so the machine never stops and held inputs are never dropped by the figures; a runtime that destroys a machine instance drops its held inputs with it, as an SDL agent's input port goes with the agent. (f) **Parameters.** A held input keeps the parameters it arrived with (for a received frame, its P/F, N(r), N(s) and payload). (g) **Reporting.** The released inputs are reported in `DispatchResult.Replayed`, in order, and traces assert them under `replayed:`; the saving step reports the transition id `save`. Nothing in the explorer or `TwoStation.tla` uses any of this yet; `Ax25DataLinkTables.tla` carries the saves as an unused `Saves` constant, and modelling them in both checkers is the later half of #97.

## Novel findings

Hypotheses, not findings: every one still has to be reproduced against a real implementation before it is worth filing (the brief's evidence-class rule). H1 has since been filed as ax25spec#91, H5 as ax25spec#168, H6 as ax25spec#170, H7 as ax25spec#171 H8 as ax25spec#178, and H9 on ax25spec#12 (fix in ax25spec PR #180); the others have not. H5 and the observation after it come from coverage batch 4, H6 and H7 from coverage batch 5.

**H1. A station can enter TimerRecovery and never leave it.** Shortest trace: 20 steps, budget 1, no SREJ, A sends 2 frames and B sends 3 (`ab2-ba3-b1-k2-srejoff-fdrop` in the grid; a 19-step budget-2 variant is `HypothesisH1_...` in the suite). A's second frame is lost; A's T1 expires and it polls; B's F=1 answer acknowledges only the first frame (nr=1), so A retransmits and stays in TimerRecovery (figc4.5 `t18_rr_received_yes_yes_no`); the retransmission gets through, and the acknowledgement for it arrives on B's next I frame (N(r)=2). In TimerRecovery that I frame runs `Check_I_Frame_Acknowledged`, whose nr = V(s) path stops T1 and starts T3, but the state stays TimerRecovery: figc4.5 leaves it only on an F=1 response, and it has no T3 arm. A now sits in TimerRecovery with T1 stopped, nothing outstanding, RC = 1, and nothing that will ever move it. Consequences the figure implies: the T3 keepalive is dead (no arm), and the next data A sends restarts T1 with RC still 1, so the retry counter creeps (which is where #9 bites). Does it depend on a choice the figure did not make? The only modelling choice involved is treating TimerRecovery as non-quiescent, which §4.4.5.1 supports ("the timeout condition is cleared by the reception of an acknowledgement for the sent frame(s)"); the retransmission pinning re-emits the frame as the figure intends and the quiescent-timeout rule only orders events realistically. Calibration: direwolf's `i_frame()` (src/ax25_link.c at eda1383f, the erratum note before its `state_4_timer_recovery && va == vs` exit) says "I noticed that we sometimes got stuck in state 4 and rc crept up slowly even though we received 'I' frames with N(R) values indicating that the other side received everything that we sent. Eventually rc could reach the limit and we would get an error", adds a transition to state 3 on full acknowledgement, and notes "a similar situation for RR/RNR for cases other than response, F=1". So an implementation has independently hit this and coded around it, and it relates the finding to #9. On the small grid this is the dominant signature: 66 of the 116 violating cells.

**H2 (a nuance under #13, not a separate claim). `Invoke_Retransmission` called with N(r) = V(s) pushes eight frames that do not exist.** figc4.7 draws the loop as a do-while (`loop_while ... test: tail` in `subroutines.sdl.yaml`), so with X = V(s) = N(r) the body runs once before the test and then seven more times round the modulus. It is only reachable through an incoherent REJ: on the pre-40 tables from a duplicate, on the current tables only at k = 7. Every real implementation loops while N(s) != V(s) and sends nothing. Whether this is a figure nit or simply unreachable once #40 and the k constraint hold is for the working group; it depends on the pinned choice that a frame with no retained copy is an error rather than skipped.

**H3 (a note under #43, not a separate claim). The DL-FLOW-OFF and DL-FLOW-ON busy arms emit RNR / RR with no N(r) staging.** figc4.4 t05's busy arm is "Set Own Receiver Busy, RNR Response, Clear Acknowledge Pending" and t06's is "Clear Own Receiver Busy, RR Command, Clear Acknowledge Pending" (figc4.5 has the same pair with explicit F = 0 / P = 0); neither draws an `N(r) := V(r)` box, unlike every other RR/RNR emission in the figures (Transmit_Enquiry, Enquiry_Response, the I-frame arms). Under the interpreter's staging policy (pinned semantic 3: an emission without a staged N(r) is an error, "the table omitted the staging assignment") both arms are interpreter errors. They are unreachable on the current tables, because nothing sets own-receiver-busy from not-busy, which is #43 itself; the moment #43 is fixed by swapping the branches, the explorer's first FLOW_OFF will hit a machine error on the RNR. Pinned by `Defect43_Note_The_Busy_Arms_Emit_RNR_And_RR_Without_N_r_Staging` at the interpreter level. Does it depend on a choice the figure did not make? Yes, entirely: every implementation sends N(r) = V(r) on that RNR, and the figure almost certainly means that; whether a #43 fix should add the box or the reading "an RNR/RR always carries V(r)" should be stated is for the working group. It is filed here so the fix does not trade one xfail for a machine error.

**H4 (recorded on ax25spec#95, not filed as a figure defect). Under reordering, a stale N(r) resets the link.** Shortest traces: 11 steps (`ro-stale-rej`) and 9 (`ro-stale-i`). A frame carrying an acknowledgement is overtaken by a newer one (B's REJ nr=0 by B's RR nr=1, or A's I frame nr=0 by A's RR nr=1), so it arrives with N(r) below the receiver's V(a). figc4.4 checks V(a) <= N(r) <= V(s), finds an N(r) error and re-establishes, and the frames outstanding at the resetting station are never sent again. Layer 3 is told: in `ro-stale-rej` the resetting A gets DL-ERROR J and then DL_CONNECT_confirm, B gets DL-ERROR F; in `ro-stale-i` B gets DL-ERROR J and A, taking the SABM in Connected, DL-ERROR F and DL_CONNECT_indication. Losing data on a reset is the designed behaviour, already the subject of ax25spec#50 and #114. The one silent part: in `ro-stale-i` B's queued, never-sent b1 is discarded by `Establish_Data_Link` through `Clear_Exception_Conditions` ("Discard I Queue Entries"), and B's layer 3 hears only DL-ERROR J, with no DL-CONNECT. With one more reorder (`ro-reset-dup`, 18 steps) a copy of a frame sent before the reset arrives after it and is delivered a second time, because the new link restarts at N(s) = 0. Both the trigger and the duplicate need a reordering channel, which the specification implicitly assumes cannot happen: §6.4.11's valid N(R) range and §6.5's restart of the numbering on a reset both presuppose order. Pinned semantic 6 keeps reordering off for that reason; ax25spec#95 is where it is verified.

**H5 (filed as ax25spec#168). A peer that stays busy while a frame is outstanding is disconnected after N2 polls.** Shortest trace: 18 steps (`busy-b-long`), no faults, A sends 2 at k = 4, B enters its busy condition once A's first frame is out and stays busy. A receives the RNR, holds a1, and polls on T1 (figc4.4 `t12_t1_expiry`, RC := 1); B answers RNR F=1 with N(r) = 0 while A's V(s) = 1, which takes figc4.5 `t19_rnr_received_yes_yes_no`: set peer busy, stop T1, V(a) := N(r), Invoke Retransmission, stop T3, start T1, set Acknowledge Pending, and RC unchanged. The next T1 expiry polls again with RC + 1 (`t21_t1_expiry_no`); after N2 = 4 RNR answers `t21_t1_expiry_yes_no` disconnects with DL-ERROR I, and each RNR answer has re-queued a0 once more (four copies queued, held by the peer-busy pop arm; that part is #52's amplification). With nothing outstanding the same answer takes `t19_rnr_received_yes_yes_yes` (stop T1, start T3, RC := 0, Connected) and the link survives any busy period, so whether a long busy period kills the link depends only on whether a frame happened to be outstanding when the peer went busy, which is the usual case (the RNR is sent because the peer cannot take more). §6.4.9 describes the other behaviour for both: "If an RNR frame is received in response to this poll, T1 is stopped and T3 is started again". DL-ERROR U ("N2 timeouts: extended peer busy condition") exists; its arm (`t21_t1_expiry_yes_yes_yes`) needs V(s) = V(a), which an RNR answer never leaves behind, but it is reached through lost polls while the peer stays busy, as #168 itself says (`dl-error-u`, coverage batch 6's review). The July 1998 edition draws one column for RR and RNR received in Timer Recovery: a response with F = 1 stops T1, sets V(a), and if V(s) != V(a) invokes retransmission and stays in Timer Recovery with no T1 restart and no T3 start, so a 1998 station in the same position, its pops held by the busy peer, never polls again and waits for the busy station's clearing RR, which a single loss strands; the 2017 redraw added Stop T3, Start T1 and Set Acknowledge Pending on that branch (green on the 2017 figure), which is what makes the RC count. Neither edition does what §6.4.9 says. Depends on a choice the figure did not make? Only the modelling choice that a busy period can outlast N2 T1 periods (`--long-busy`); the channel is the default one. Not reproduced against an implementation.

## Interpreter changes made for the explorer

All in `codegen/src/Packet.Sdl.Interpreter`, kept to the smallest set that leaves every golden trace's observed effects unchanged:

- `Machine.cs`: `QueueEntry` (label, original N(s), retained payload) replaces the string queue internally (`Queue` still returns labels; `QueueEntries`, `SavedFrames`, `RetainedFrames` are new read-only views); the retained send history is filled on every "I Command" emission and pruned to [V(a), V(s)) after each dispatch (`PruneRetained`); "Push Old I Frame onto Queue" / "Push Old I Frame N(r) on Queue" go through `QueueInsertOld`; `Dispatch` routes a popping old frame in Connected/TimerRecovery to `RetransmitOldFrame` (pinned semantic 1); `DL_DATA_indication` carries the delivered label via a `_deliverData` scratch set by "Retrieve Stored V(r) I Frame"; a private copy constructor and `Clone()`.
- `Effects.cs`: `FrameEffect` gains an optional `Data` (payload label), `UpperEffect` an optional `Detail`; both render the extra field only when present.
- `Machine.cs` (coverage batch 5): "UI Command" carries the DL-UNIT-DATA Request's payload label, and `DL_UNIT_DATA_indication` the received UI frame's (`Ax25Meaning.tla` the same).
- The `vr_lt_ns_lt_vr_plus_k` atom binding (`NsInReceiveWindow`) is main's.
