# The two-station explorer

`codegen/src/Packet.Sdl.Explorer` composes two reference-interpreter Data Link machines (`Packet.Sdl.Interpreter`, station A and station B) over a modelled channel and explores every interleaving breadth-first from a seeded state, checking cross-station invariants after every step. It is steps 2 and 3 of the decision brief `packethacking/ax25spec` `docs/fuzzing-the-figures.md`: the calibration suite that proves the invariants have teeth by rediscovering known figure defects, and the two-station progress model built on the interpreter from #75.

Breadth-first means the first counterexample found is the shortest. Every counterexample prints as a step log: which station, the injected event with its fields, the transition id that fired, the effects emitted, and both stations' key variables after the step.

Run it:

```sh
dotnet run --project codegen/src/Packet.Sdl.Explorer -- --tables spec/json --frames-ab 2 --frames-ba 0 --k 4 --srej --budget 1 --faults drop,dup
dotnet run --project codegen/src/Packet.Sdl.Explorer -- --frames-ab 2 --flow-control B                      # #43 in three steps
dotnet run --project codegen/src/Packet.Sdl.Explorer -- --frames-ab 0 --seed awaiting-v22 --peer v20-frmr --selective-progress   # #45 in four
dotnet run --project codegen/src/Packet.Sdl.Explorer -- --frames-ab 0 --seed awaiting-v22 --peer v20-dm     # #48 in two
dotnet run --project codegen/src/Packet.Sdl.Explorer -- --help
dotnet test codegen/tests/Packet.Sdl.Explorer.Tests        # the calibration suite
```

A second checker, TLC over a TLA+ model generated from the same JSON tables, reproduces this explorer move for move and is compared with it row by row: see `docs/tla.md`.

Exit code 0 means no violation in the exhaustively explored bounded space, 1 means an invariant fired (the counterexample is printed), 2 means a depth or visited-state bound was hit before the space was exhausted (the liveness checks were skipped; this is never reported as "no violation").

## The model

**System state.** Both machines' full state (state name, V(s)/V(r)/V(a), RC, flags, I-frame queue with its retransmission bookkeeping, saved out-of-sequence frames, retained sent frames, T1/T3 symbolic status), the two channel queues (frames in flight A to B and B to A, each an ordered list of concrete frames: type, command/response, P/F, N(r), N(s), payload label), each station's owed `LM_SEIZE_confirm`, the remaining fault budget, the delivery and acknowledgement counters the invariants need, each station's layer-3 flow state ("flow off" flag and completed FLOW_OFF/FLOW_ON rounds), and, when station B is the v2.0 stub peer, whether the stub is connected. A canonical serialisation of all of it is the key of the visited set.

**Enabled moves** (each is one BFS edge):

- deliver the head frame of either channel to its receiver as the matching `*_received` event with `pf`, `command`, `nr`, `ns`, `data` filled in from the frame and the environment atoms `able_to_establish` = true, `info_field_length_le_N1_and_content_is_octet_aligned` = true;
- a channel fault on a head frame while the budget lasts: drop it, duplicate it (deliver it and leave a copy at the head), or reorder (swap the first two). Each kind is switchable (`--faults drop,dup,reorder`); `--drop-scope interior-i` restricts drops to I frames that are not the last submitted in their direction;
- `I_frame_pops_off_queue` at a station whose queue is non-empty, but only when the pop changes something (a window-full or peer-busy pop pushes the frame straight back and is a self-loop);
- `LM_SEIZE_confirm` at a station that owes one;
- `T1_expiry` at a station whose T1 is running, only when both channel queues are empty, no confirm is owed and no productive pop is pending anywhere: the quiescent-timeout abstraction. A timer fires only once everything in flight has been delivered or lost. This keeps the space finite and is sound for the progress properties, and it loses premature-timeout interleavings (a T1 that fires while frames are still on the air);
- `DL_FLOW_OFF_request` and `DL_FLOW_ON_request` at a station the scenario lets layer 3 flow-control (`--flow-control A|B|both`), only on a page with a direct arm for them (Connected, TimerRecovery: layer 3 does not flow-control a link that is not up). FLOW_OFF is enabled once the station has delivered `--flow-off-after` frames upward (default 1) and a round is left; FLOW_ON is enabled whenever flow is off; FLOW_OFF then FLOW_ON is one round and `--flow-rounds` (default 1) bounds the rounds so the space stays finite. The simple shape "B turns flow off once after its first delivery, then on again later" is the default. Neither move is a fault, so the liveness checks may use them; neither affects the quiescent-timeout rule (a layer-3 decision is not work in flight);
- with `--data-after-confirm` (disconnected seed only), `DL_DATA_request` for a station's next frame once its data link has reported the link up to layer 3 (`DL_CONNECT_confirm` at A, `DL_CONNECT_indication` at B), one frame per move, in order. Layer 3 stops submitting when its data link reports the link down (`DL_DISCONNECT_indication` or `DL_DISCONNECT_confirm`) and resumes, with its next unsent frame, after the next `DL_CONNECT_confirm` or `DL_CONNECT_indication` (pinned semantic 13). It is not a fault, so the liveness checks may use it; a station with a frame ready to submit counts as pending work for the quiescent-timeout rule, so T1 does not fire past it;
- with `--data-before-confirm` (`ExplorerOptions.DataBeforeConfirm`, which implies `--data-after-confirm`), A's layer 3 does not wait for its confirm: it treats the link as usable from the seed on, so its submissions are moves that can come before the UA (where figc4.2 discards them while layer 3 initiated, ax25spec#161) or after it. B's layer 3 still waits for its indication. This is the move form of the `d161-data-before-confirm` seed;
- with `--release A|both` (`ExplorerOptions.Release`), `DL_DISCONNECT_request` from that station's layer 3 (or either station's), once, on an established link (Connected or TimerRecovery, the pages with a direct arm for it), once every frame either station submitted has been delivered upward at its peer: the application knows the exchange is complete. It is not a fault, so the liveness checks may use it. Like flow control it is a layer-3 decision, not work in flight, so it does not hold back T1. Quiescence then means released: both stations Disconnected after a layer 3 issued its release, nothing in flight or queued, everything delivered, no owed confirms. Table-driven peer only. A consequence worth knowing: the release masks #91 (H1 below), because it takes a stranded station out of TimerRecovery, so a release scenario cannot see #91;
- with `--release-early` (`ExplorerOptions.ReleaseEarly`, with `--release`), the release may also come while the link is still being set up (AwaitingConnection, AwaitingV22Connection), not only on an established link, under the same delivery gate. Figures C4.2 and C4.6 draw a Save (Requeue) for DL-DISCONNECT Request there, which codegen does not emit yet (packet-net/ax25sdl#97), so on the generated tables the request goes to the page's upper-layer catch-all and is dropped; the rows say so rather than modelling the Requeue;
- with `--reconnect A|both` (`ExplorerOptions.Reconnect`), `DL_CONNECT_request` from that station's layer 3 (or either's), once, on a live or waiting link (AwaitingConnection, AwaitingV22Connection, Connected or TimerRecovery), once every frame either station submitted has been delivered upward at its peer (the release's gate). The layer 3 then waits for the answer, `DL_CONNECT_confirm` or `DL_DISCONNECT_indication`, and no state counts as quiescent while it waits (the reconnect answer rule, pinned semantic 13). Not a fault, not work in flight. Table-driven peer only;
- with `--accept-give-up` (`ExplorerOptions.AcceptGiveUp`), no new move but a wider quiescence, the give-up rule: see the Quiescence invariant below and pinned semantic 12;
- `T3_expiry` is disabled in this version (figc4.5 has no T3 arm at all, so a T3 expiry in TimerRecovery would be an interpreter error rather than a protocol event; leaving T3 out of the connected phase is a scope decision, not a claim).

**Data submission.** All frames are submitted up front: the seeded state has every `DL_DATA_request` already applied, so the queues start full (labels `a0..`, `b0..`). This loses interleavings where data arrives after recovery has begun. The exception is `--data-after-confirm` (`ExplorerOptions.DataAfterConfirm`) on the disconnected seed: then nothing is submitted in the seed, and each station's layer 3 submits its frames by moves once its link is up, as a well-behaved layer 3 would. B may have data in that case. Layer 3 follows what its data link tells it (pinned semantic 13): it stops on `DL_DISCONNECT_indication` or `DL_DISCONNECT_confirm` and resumes after the next `DL_CONNECT_confirm` or `DL_CONNECT_indication`; a DL-ERROR or a re-establishment the data link started itself does not stop it, because layer 3 still believes the link is up (figc4.2 keeps that data while Layer 3 Initiated is clear). It never offers a frame twice: what it had offered before the link went down, and the data link then discarded, stays offered and undelivered, so a scenario that loses it can never be clean. Until coverage batch 3 the link-up flag never cleared, so after a disconnect layer 3 submitted `DL_DATA_request` to a station in Disconnected, which both tools reported as a MachineError (`l3-down-mod128` was one at 15 steps); the stop rule and the routing of upper-layer primitives to their catch-all (pinned semantic 5) removed it. With `--data-before-confirm`, A's layer 3 starts out treating the link as up.

**Seeds.** `connected`: both stations Connected with zeroed variables, T3 running, modulo 8, k (default 4, 1..7), SREJ on or off (SREJ implies version 2.2 on both), N2 (default 4). `disconnected`: both Disconnected, A has issued `DL_CONNECT_request` (with `--mod128`, A is seeded at modulo 128 so that sends SABME) and then submitted its data (figc4.2 discards data offered while layer 3 initiated, as the July 1998 edition of the figure labels it, with no indication to layer 3: ax25spec#161), or, with `--data-after-confirm`, holds it until the link is up; `--peer-declines-sabme` makes the table-driven B answer SABME with DM while accepting SABM (`able_to_establish` = false for SABME). `awaiting-v22`: A is already in AwaitingV22Connection with its SABME P=1 in flight (RC 1, layer 3 initiated, T1 running, modulo 128, version 2.2: the initial state of the golden trace `frmr-fallback-downgrades-to-sabm`, plus the frame that put it there), B Disconnected, no data. It exists because on the current tables a cold `DL_CONNECT_request` never reaches figc4.6 (#44 routes the SABME initiator to figc4.2), so the figc4.6 columns that #45 and #48 live in are unreachable from the `disconnected` seed; this seed enters them directly, as #44's fix would.

**Station B as a v2.0 stub peer** (`--peer v20-frmr|v20-dm`, connect-phase seeds only). A hand-written model of an October 1984 AX.25 v2.0 station, not a table-driven machine: the v2.2 figures cannot play a peer that does not know SABME. It answers SABME with FRMR (`v20-frmr`, the figc4.6 t14 trigger) or with DM F=1 (`v20-dm`, the #48 case), accepts SABM with UA and is then "connected, modulo 8", answers a polled supervisory command with RR F=1, and ignores responses. It has no data phase: both frame counts must be 0 and the scenario ends at "link established with modulo 8", which is the stub's quiescent condition. That was the smaller of the two options the brief allowed (the other being a minimal RR-acknowledging data phase) and it is enough because every defect under test is in the connect phase. Its rules are pinned semantic 10 below, with the 1984 citations. It is the environment: no invariant is checked on it, and a frame outside its rule set (an I frame) is a machine error rather than something silently absorbed. No fixed tables exist to discriminate #45 or #48 against; the control cases are the same stub with a v2.0 (modulo 8) initiator, which connects with SABM, UA and no timer, and a table-driven v2.2 peer answering the seeded SABME with UA.

**Bounds.** Frames per direction 0..3 in the grids (the code takes any non-negative count; the fault-free #54 rows use 9), budget 0..3, k 1..7, N2 2..4, flow-control rounds (default 1), a depth cap (default 80) and a visited-state cap (default 400 000). Sizes on the current tables: 3+3 frames with budget 1 is about 51 000 states in 2.4 s; 3+3 with budget 2 is about 600 000 states in 20 s; flow control at one station roughly triples a cell (the largest cell above passes 1.2 million); the connect-phase cells against the stub peer are under 110 states; every calibration case runs well under a second.

## Invariants

Each is individually switchable (`--disable ...`) so the calibration suite can say which one fires.

- **Defined state**: both stations are in a state the tables define.
- **Sequence sanity** (ported from packet.net's `InvariantChecker`): V(s)/V(a)/V(r) in range, outstanding frames (V(s) minus V(a), mod 8) never exceed k, and the SREJ exception count never exceeds k (each outstanding SREJ names a distinct missing frame inside the window, so a coherent receiver has at most k-1; the bound turns the #42 runaway, whose count is unbounded, into a verdict instead of a depth-bound hit).
- **Delivery** (ported from `InvariantChecker`): the sequence of payload labels each station delivered upward is an exact in-order prefix of what the peer submitted: no gap, no duplicate, no reorder. `DL_DATA_indication` carries the delivered label, which is how order is observed.
- **Reject coherence** (ax25spec#40 stated exactly, generalised). Emitter side: when a station emits REJ or SREJ with N(r) = x, x must be a frame it has not received in sequence (x = V(r), or a not-yet-held frame inside its receive window). Receiver side: when the peer receives that REJ/SREJ, x must be inside the peer's outstanding set [V(a), V(s)). The report says which side failed. The receiver-side check is strict for REJ too: the brief's option of accepting REJ with N(r) = V(s) as a pure acknowledgement is available as `--rej-may-equal-vs` but off by default, because on a FIFO channel a REJ can only carry the receiver's V(r) at a moment when it had already received a frame above V(r), so the sender had sent frame N(r) and V(s) > N(r) ever since; N(r) = V(s) can only come from a reject raised on a stale duplicate (the #40 class), and figc4.7's `Invoke_Retransmission` is a do-while that then pushes I(V(s)), a frame that was never sent.
- **Acknowledgement coherence**: a station's V(a) never advances past the number of frames the peer has delivered upward. Absolute (unwrapped) counters are tracked per direction alongside the modulo values, so this is exact; a link (re)establishment zeroes the variables without acknowledging anything and is excluded from the count.
- **Flow-off delivery** (`flow-off-delivery`): no `DL_DATA_indication` is delivered at a station while its layer 3 has flow off (after its `DL_FLOW_OFF_request`, before its `DL_FLOW_ON_request`). This is what DL-FLOW-OFF is for: once the busy condition is up, figc4.4's own `I frame received / own receiver busy? yes` arm discards the frame, so a correct figure never delivers while flow is off, even for a frame that was already on the air.
- **Busy tracks flow** (`busy-tracks-flow`, the cheaper check): after `DL_FLOW_OFF_request` the station's own-receiver-busy condition is set, and after `DL_FLOW_ON_request` it is clear. §6.4.10 ("Whenever a TNC enters a busy condition, it indicates this by sending an RNR response") is what DL-FLOW-OFF exists to trigger, and the figure's own DL-FLOW-ON arm assumes it: it only acts when busy is set.
- **Quiescence under a fair channel** (liveness, on the reachable-state graph): after the BFS, from every reachable state a fault-free path must lead to a quiescent state (both Connected, both channels and queues empty, V(s) = V(a) on both, all submitted data delivered, no owed confirms). Implemented as reverse reachability from the quiescent states over the non-fault edges of the whole graph ("the channel eventually stops faulting"); a state that cannot reach quiescence is reported with the path to it and its enabled moves. That is "no unclearable exception" and "livelock" as a graph property instead of a timeout. With the give-up rule (`--accept-give-up`, off by default) a link that ran out of retries for a reason the faults explain is at rest too: a station that exhausts N2 (a T1 expiry that takes it to Disconnected) has given up honestly when at least as many frames were dropped since that station last made progress as its retry loop has attempts, and a settled honest give-up (some station gave up honestly and none unjustifiably, each station Disconnected or at rest as above, nothing in flight or owed) with everything delivered is quiescent. One that lost data is not: a deadlock there is reported as **give-up loss** (`GiveUpLoss`), so the loss is visible as such rather than accepted. An unjustified give-up never rests: with the rule on, no state counts as quiescent once a station has given up without the losses to justify it, so #9, whose give-up comes after the acknowledgements progressed, stays a deadlock. The cheaper **deadlock** check (a terminal, non-quiescent state) runs first and is sound even when a bound was hit. With the v2.0 stub as B, "B at rest" is just "the stub is connected". The state reported for a liveness failure is the shallowest one that cannot reach quiescence and has no non-fault edge (non-T1 too, for the timer-free check) to any other state, i.e. where the model is actually stuck; the seed is usually non-reaching as well, but the stuck state is the one that reads as a counterexample.
- **Timer-free progress** (off by default, `--selective-progress`): quiescence must be reachable without any `T1_expiry` move. In the data phase this is selective-recovery progress: with SREJ negotiated and a fault-free future, a loss is recovered without a timeout; it is only meaningful there with `--drop-scope interior-i` and drops only (losing a trailing frame, an SREJ or an acknowledgement can only be recovered by T1). It holds on the current tables for an interior loss with 2 frames; it never gets to run on #42 (see the score). In the connect phase, against the v2.0 stub peer with no faults, the same check reads as "the v2.0 fallback re-establishes without a timeout": a FRMR (or DM) to our SABME should be answered by a SABM straight away, and a connect that only comes up because figc4.2's T1 retry happens to send SABM has not fallen back at all. That is the check that sees #45 (and #44 masking it); it now has discriminating calibration cases.
- **Machine error** (always on): the interpreter threw. Either an unbound verb/atom, a non-deterministic table, a state page with no arm (direct or catch-all) for a received frame, or a pinned-semantics gap such as a retransmission of a frame the station never sent.

## Pinned delegated semantics

The figures delegate some behaviour to "the implementation". Every choice the explorer or the interpreter makes in those gaps is listed here, with the citation that settles it or a note that it is a judgement call. Ask of every counterexample: does it depend on one of these?

1. **Retransmission** (`Machine.cs`, `RetransmitOldFrame`; `QueueEntry`; `RetainedFrames`). `Invoke_Retransmission` (figc4.7) backtracks V(s) to N(r) and loops "Push Old I Frame onto Queue" until V(s) returns to X; the figc4.4/4.5 SREJ arms do "Push Old I Frame N(r) on Queue". The #75 interpreter models these as re-queueing and restores V(s), so a re-pop through the table's fresh-frame path would renumber the frames from V(s) (its ambiguity #1) and loss recovery could never complete. Pinned the way every real implementation does it: the station retains a copy of every I frame it has sent, keyed by N(s), from V(a) upward (pruned to [V(a), V(s)) after each dispatch); the two push verbs re-queue an entry carrying the original N(s) and the retained payload; when such an entry pops in Connected or TimerRecovery it is re-emitted with its original N(s), the current V(r) as N(r) and P = 0, V(s) is untouched, the peer-busy and window-full pop checks do not apply (the frame is already inside the window), Acknowledge Pending clears (the frame carries an acknowledgement) and, mirroring the fresh-frame pop, T1 starts (stopping T3) if it is not already running. The reported transition id is `pinned:retransmit_old_i_frame`. Citations: packet.net `src/Packet.Ax25/Session/ActionDispatcher.cs` (`PushOldIFrameOntoQueue` maps to `EmitOldIFrame(tx, ctx.VS)`, `PushOldIFrameNrOnQueue` to `EmitOldIFrame(tx, N(r))`, both emitting directly with the original N(s)); direwolf `src/ax25_link.c` `resend_for_srej` and the `invoke_retransmission` loop; prose §6.4.7 and §6.4.8 ("retransmits the I frames"). Two consequences are deliberate: a re-queued frame the station holds no copy of (never sent, or already acknowledged) is an interpreter error at the pop, not a silently skipped frame (packet.net skips it via `IsOutstanding`; that sender-side guard is exactly what the brief says absorbed the #40 symptom, so the model refuses to have it); and a frame that is re-queued twice (a duplicated REJ, say) is sent twice, as the figure says. The existing golden traces assert the re-queue effects and queue labels, which are unchanged.
2. **Link multiplexer.** `LM_seize_request` is answered by the local multiplexer with `LM_SEIZE_confirm` to the same station; it is not a peer frame. Modelled as a boolean "owed" flag per station (a second request before the confirm is idempotent; the figure's own `ack_pending` flag already collapses them). `LM_release_request` and `LM_data_request` are no-ops. When the station's current page has no `LM_SEIZE_confirm` arm (after a reset) the confirm is routed to `all_other_primitives__from_lower_layer`. Judgement call, consistent with C4.2's description of the primitives.
3. **Interpreter policies adopted from #75** (see `docs/golden-traces.md`): transition guards evaluate against the pre-transition state, subroutine path guards and loop predicates live; P/F/N(s)/N(r) staging registers reset per dispatch and an emission without staged N(r)/N(s) is an error; the I-frame queue is a FIFO, `DL_DATA_request` joins the tail, pushed-back and re-queued frames enter at the head preserving order; `Check_I_Frame_Acknowledged` is exactly the figc4.7 subroutine table (no extra semantics); "Save Contents of I Frame" stores the frame in the receive buffer keyed by N(s) and "Discard Contents of I Frame" is a no-op, so on the SREJ-enabled REJ arm (figc4.4 `..._no_yes_no_yes`, which draws Save then Discard) the saved copy stays in the buffer and is drained later; the environment atoms default to true; subroutine call labels bind through the explicit alias map.
4. **`DL_DATA_indication` carries the delivered frame's payload label** (`UpperEffect.Detail`), for the arriving frame on the in-sequence arm and for the retrieved frame inside the drain loop ("Retrieve Stored V(r) I Frame" sets the label the next indication carries).
5. **Catch-all arms.** A frame whose `*_received` event has no arm on the current page is delivered as that page's catch-all: `all_other_commands` (Disconnected, commands), `i_or_s_command_received` (AwaitingRelease), `all_other_primitives__from_lower_layer` (the Awaiting* pages, responses). An upper-layer primitive (`DL_DATA_request`, `DL_CONNECT_request`, `DL_DISCONNECT_request`, the seed's injections included) with no arm on the page goes to its `all_other_primitives__from_upper_layer` catch-all, which every Data Link page has and none acts on (coverage batch 3; before it, only frames were routed and such a primitive was a machine error). A page with neither is a machine error. Judgement call from the figures' own "all other" columns. One consequence is recorded rather than modelled: figc4.2 and figc4.6 draw a Save (Requeue) for DL-DISCONNECT Request, which codegen drops (packet-net/ax25sdl#97), so on the generated tables that request reaches the catch-all and is lost; `release-early-*` show it.
6. **The channel** is a FIFO per direction; a duplicate is a copy left at the head, so it arrives immediately after the original; reordering (swap the first two) exists but is off by default because a single AX.25 channel does not reorder and the figures' N(r) validity checks presuppose order. Judgement call; the calibration scenarios use drop and dup only, except the `ro-*` rows of coverage batch 2, which reorder to reach the N(r)-error arms (ax25spec#95 is the verification item for reordering). Reject coherence presupposes a FIFO channel (a reordered reject can legitimately name a frame already acknowledged), so the reorder rows that reorder rejects run with it off.
7. **Quiescence requires Connected.** A station in TimerRecovery with everything acknowledged is not quiescent, following §4.4.5.1 ("the timeout condition is cleared by the reception of an acknowledgement for the sent frame(s)"). `--quiescence-accepts-timer-recovery` is a triage aid that relaxes this so a grid run can look past hypothesis H1.
8. **Timers are symbolic** (running/stopped/expired only), so anything numeric (T1 value, SRT, Karn sampling) is out of the model's reach.
9. **Version flags.** `version_2_2` is seeded equal to `--srej` (a link using SREJ has negotiated v2.2, §4.3.2.4 and §6.3.2); modulo is 8 on both sides except A under `--mod128` on the `disconnected` seed (set by hand, since the tables never set it; with `--data-after-confirm` this reaches the data phase too) and the `awaiting-v22` seed (A at modulo 128 with version 2.2 set). The tables themselves never assign the modulus (#54: the figc4.7 `Set_Version_2_0` / `Set_Version_2_2` subroutines, which would, are never invoked; the pages call the flag verbs), so an A that falls back to v2.0 keeps modulo 128 in this model, and a B that accepts SABME keeps modulo 8. Within 8 frames that has no wire effect the abstract frame model can see; past the wrap it does (the #54 row of the calibration table).
10. **The v2.0 stub peer** (`V20Peer.cs`). Each rule cites the October 1984 text in `spec-sdl/v2.0/` (a scan; read page by page). SABME is a control field a v2.0 station does not know: `v20-frmr` answers FRMR with F = P under §2.3.4.3.3.1 ("The FRMR response frame is sent to report that the receiver of a frame cannot successfully process that frame ... 1. The reception of an invalid or not implemented command or response frame", where "an invalid or not implemented command or response is defined as a frame with a control field that is unknown to the receiver"); that is the trigger figc4.6 t14 is drawn for (v2.2 §4.3.3.9 "FRMR is retained for compatibility with older versions", §6.3.2 "a version 2.0 connection is made", §6.5). `v20-dm` answers DM with F = 1 under §2.3.4.3.5 ("While a DXE is in the disconnected mode, it will respond to any command other than a SABM or UI frame with a DM response with the P/F bit set to 1") and §2.4.3.4.3; both readings are legal v2.0 behaviour, and XRouter takes the DM one on the wire (#48). SABM is accepted with UA F = P (§2.3.4.3.4 "The UA response frame is sent to acknowledge the reception and acceptance of a SABM or DISC command frame", §2.4.3.4.2) and the stub is then connected at modulo 8. DISC: UA F = P when connected, DM F = 1 when not (§2.4.3.4.1). Any other command while disconnected: DM F = 1 (§2.3.4.3.5). A supervisory command with P = 1 while connected: RR F = 1, N(r) = 0 (§2.4.2); with P = 0 nothing (no T2 delayed acknowledgement). UI frames and all responses are ignored. No timers, no unsolicited frames, no data phase (an I frame is a machine error; the seeds enforce zero frames). The one judgement call is F = P rather than F = 1 on the FRMR (§2.3.4.3.3 does not say; figc4.6 t14 has no F guard so it cannot matter here); v2.2 §4.3.3.5 is the same DM rule in the current prose.
11. **Layer-3 flow control** is a scenario input, not a peer frame: the moves are described under the model. The round bound and the delivered-frames threshold are judgement calls that keep the space finite and put the FLOW_OFF where it can be observed (after at least one delivery, so the next delivery is the test). Layer 3 is assumed to flow-control only an established link (the moves need a direct arm on the page).
12. **The give-up rule** (`--accept-give-up`, `ExplorerOptions.AcceptGiveUp`; TLA+ constant `AcceptGiveUp`). A give-up is a T1 expiry that takes a station to Disconnected: the RC = N2 arms of figc4.2, figc4.6, figc4.3 (Awaiting Release) and figc4.5. It is honest when the drops since the station's last progress reach the attempts its retry loop has before it gives up. The attempts are read off the figures, not chosen: `Establish_Data_Link` sets RC := 1, so figc4.2 and figc4.6 give up after N2 transmissions (threshold N2); DL-DISCONNECT sets RC := 0, and Connected's T1 expiry sets RC := 1 only after a first loss, so Awaiting Release and Timer Recovery give up after N2 + 1 (threshold N2 + 1). Judgement calls, each chosen so the rule errs towards refusing a give-up: only drops count as losses (a duplicate or a reorder loses nothing); a drop on either channel counts for both stations (lenient, but bounded by the next point); progress, which clears a station's count, is its own frames being acknowledged further (the acknowledgement counter of the ack-coherence check advancing) or its layer 3 being told the link came up (DL-CONNECT confirm or indication), and it is deliberately not RC, which is what #9 gets wrong. A station left Connected with nothing queued or outstanding after its peer gave up counts as settled only if nothing its peer sent at or after the give-up reached it: such a station never heard the give-up (its DM was lost, or there was none), and on the air its T3 would probe and find the peer gone, which the model cannot show because T3 is outside it. A station that received the DM and stayed up is not settled, so a figure that ignores the DM is still caught (`seeded-dm-ignored`). Since T1 only fires with both channels empty, every frame that reaches a station after its peer gave up was sent at or after the give-up, so the harness only has to note that one arrived. The loss count is not reset when a retry loop starts: drops from before the loop (on either channel, since the station's last progress) count towards it too. That could let a give-up through whose own loop lost fewer frames than it has attempts, for instance a #9-like early give-up that follows an unacknowledged loss earlier in the exchange; the rule accepts that leniency rather than define where a loop starts independently of the figures' RC. The thresholds for Awaiting Release and Timer Recovery (N2 + 1) are not pinned by a row: on the current tables no give-up there comes before N2 + 1 failed attempts, so lowering them to N2 changes no verdict; only a defective table could tell them apart. Data lost in an honest give-up is the protocol doing what it says (DL-ERROR and DL-DISCONNECT reach layer 3), but accepting it would also accept a defect that loses data on the way down, so it is reported, under its own name. Without the rule, a release rest does not ask how the link went down: an Awaiting Release give-up after all data was delivered passes as released whether or not the faults justify it, so a release scenario whose budget reaches N2 + 1 should turn the rule on.

13. **Layer 3** (coverage batch 3). Layer 3 is the scenario, not a peer, and it is well-behaved: it submits data only while its data link says the link is up (with `--data-after-confirm`), stops on `DL_DISCONNECT_indication` or `DL_DISCONNECT_confirm`, resumes after the next `DL_CONNECT_confirm` or `DL_CONNECT_indication`, and never offers a frame twice, so data the data link discarded stays visible as undelivered instead of being dropped from the count. A layer 3 that issues `DL_CONNECT_request` on a live or waiting link (`--reconnect`) expects an answer: `DL_CONNECT_confirm` (C4.2's response to a DL-CONNECT Request) or `DL_DISCONNECT_indication` (the attempt failed); a DL-ERROR or a `DL_CONNECT_indication` alone is not an answer, and until one comes no state is quiescent, plain, released or a settled give-up. More generally, every layer 3 keeps the last link report its data link gave it (up: `DL_CONNECT_confirm` or `_indication`; down: `DL_DISCONNECT_indication` or `_confirm`), and at rest that report must match the station's state: up only while Connected or TimerRecovery, down only while Disconnected (no report yet constrains nothing). So a disconnect indication answers a reconnect only if the station really rests Disconnected, and a layer 3 told the opposite of what its station did is never at rest (the report rule, from the review of this batch, which found that a DL_DISCONNECT_indication in place of the connect confirm was accepted; `seeded-confirm-as-disconnect` pins it). One leniency is known and accepted: figc4.2 `t04_ua_received_yes_no_no` emits DL_CONNECT_confirm with Layer 3 Initiated clear (a link reset by the data link itself, with V(s) != V(a)), so if a reconnect were followed by such a reset before its own UA, that confirm would count as the answer; layer 3 cannot tell one confirm from another, and no current row takes that path. The reconnect and the early release use the release's gate (everything both sides submitted is delivered: the application has finished its exchange), and both are limited to a live or waiting link (not Disconnected, where a DL-CONNECT is the ordinary connect, and not AwaitingRelease, where neither the reset nor the release is a live request). Judgement calls: the gate keeps a reset from discarding queued data by design, which would only report the designed loss; the answer rule is what makes `reconnect-tr` a violation (without it both ends end up Connected with everything delivered), and `seeded-reconnect-swallowed` shows both tools enforce it. The rule was checked by removing it in both tools: that seeded row and `reconnect-tr` both became clean. Two implementation notes: the report rule is always on (it adds a field to the state, which changed the state counts of three batch 3 rows and of no earlier row), and both tools set the pending flag after the reconnect's own dispatch, so an arm that answered within that dispatch would be overwritten; no current arm does (each sends SABM(E) or nothing).

## Novel findings

Hypotheses, not findings: every one still has to be reproduced against a real implementation before it is worth filing (the brief's evidence-class rule). H1 has since been filed as ax25spec#91; the others have not.

**H1. A station can enter TimerRecovery and never leave it.** Shortest trace: 20 steps, budget 1, no SREJ, A sends 2 frames and B sends 3 (`ab2-ba3-b1-k2-srejoff-fdrop` in the grid; a 19-step budget-2 variant is `HypothesisH1_...` in the suite). A's second frame is lost; A's T1 expires and it polls; B's F=1 answer acknowledges only the first frame (nr=1), so A retransmits and stays in TimerRecovery (figc4.5 `t18_rr_received_yes_yes_no`); the retransmission gets through, and the acknowledgement for it arrives on B's next I frame (N(r)=2). In TimerRecovery that I frame runs `Check_I_Frame_Acknowledged`, whose nr = V(s) path stops T1 and starts T3, but the state stays TimerRecovery: figc4.5 leaves it only on an F=1 response, and it has no T3 arm. A now sits in TimerRecovery with T1 stopped, nothing outstanding, RC = 1, and nothing that will ever move it. Consequences the figure implies: the T3 keepalive is dead (no arm), and the next data A sends restarts T1 with RC still 1, so the retry counter creeps (which is where #9 bites). Does it depend on a choice the figure did not make? The only modelling choice involved is treating TimerRecovery as non-quiescent, which §4.4.5.1 supports ("the timeout condition is cleared by the reception of an acknowledgement for the sent frame(s)"); the retransmission pinning re-emits the frame as the figure intends and the quiescent-timeout rule only orders events realistically. Calibration: direwolf's `i_frame()` (src/ax25_link.c at eda1383f, the erratum note before its `state_4_timer_recovery && va == vs` exit) says "I noticed that we sometimes got stuck in state 4 and rc crept up slowly even though we received 'I' frames with N(R) values indicating that the other side received everything that we sent. Eventually rc could reach the limit and we would get an error", adds a transition to state 3 on full acknowledgement, and notes "a similar situation for RR/RNR for cases other than response, F=1". So an implementation has independently hit this and coded around it, and it relates the finding to #9. On the small grid this is the dominant signature: 66 of the 116 violating cells.

**H2 (a nuance under #13, not a separate claim). `Invoke_Retransmission` called with N(r) = V(s) pushes eight frames that do not exist.** figc4.7 draws the loop as a do-while (`loop_while ... test: tail` in `subroutines.sdl.yaml`), so with X = V(s) = N(r) the body runs once before the test and then seven more times round the modulus. It is only reachable through an incoherent REJ: on the pre-40 tables from a duplicate, on the current tables only at k = 7. Every real implementation loops while N(s) != V(s) and sends nothing. Whether this is a figure nit or simply unreachable once #40 and the k constraint hold is for the working group; it depends on the pinned choice that a frame with no retained copy is an error rather than skipped.

**H3 (a note under #43, not a separate claim). The DL-FLOW-OFF and DL-FLOW-ON busy arms emit RNR / RR with no N(r) staging.** figc4.4 t05's busy arm is "Set Own Receiver Busy, RNR Response, Clear Acknowledge Pending" and t06's is "Clear Own Receiver Busy, RR Command, Clear Acknowledge Pending" (figc4.5 has the same pair with explicit F = 0 / P = 0); neither draws an `N(r) := V(r)` box, unlike every other RR/RNR emission in the figures (Transmit_Enquiry, Enquiry_Response, the I-frame arms). Under the interpreter's staging policy (pinned semantic 3: an emission without a staged N(r) is an error, "the table omitted the staging assignment") both arms are interpreter errors. They are unreachable on the current tables, because nothing sets own-receiver-busy from not-busy, which is #43 itself; the moment #43 is fixed by swapping the branches, the explorer's first FLOW_OFF will hit a machine error on the RNR. Pinned by `Defect43_Note_The_Busy_Arms_Emit_RNR_And_RR_Without_N_r_Staging` at the interpreter level. Does it depend on a choice the figure did not make? Yes, entirely: every implementation sends N(r) = V(r) on that RNR, and the figure almost certainly means that; whether a #43 fix should add the box or the reading "an RNR/RR always carries V(r)" should be stated is for the working group. It is filed here so the fix does not trade one xfail for a machine error.

**H4 (recorded on ax25spec#95, not filed as a figure defect). Under reordering, a stale N(r) resets the link.** Shortest traces: 11 steps (`ro-stale-rej`) and 9 (`ro-stale-i`). A frame carrying an acknowledgement is overtaken by a newer one (B's REJ nr=0 by B's RR nr=1, or A's I frame nr=0 by A's RR nr=1), so it arrives with N(r) below the receiver's V(a). figc4.4 checks V(a) <= N(r) <= V(s), finds an N(r) error and re-establishes, and the frames outstanding at the resetting station are never sent again. Layer 3 is told: in `ro-stale-rej` the resetting A gets DL-ERROR J and then DL_CONNECT_confirm, B gets DL-ERROR F; in `ro-stale-i` B gets DL-ERROR J and A, taking the SABM in Connected, DL-ERROR F and DL_CONNECT_indication. Losing data on a reset is the designed behaviour, already the subject of ax25spec#50 and #114. The one silent part: in `ro-stale-i` B's queued, never-sent b1 is discarded by `Establish_Data_Link` through `Clear_Exception_Conditions` ("Discard I Queue Entries"), and B's layer 3 hears only DL-ERROR J, with no DL-CONNECT. With one more reorder (`ro-reset-dup`, 18 steps) a copy of a frame sent before the reset arrives after it and is delivered a second time, because the new link restarts at N(s) = 0. Both the trigger and the duplicate need a reordering channel, which the specification implicitly assumes cannot happen: §6.4.11's valid N(R) range and §6.5's restart of the numbering on a reset both presuppose order. Pinned semantic 6 keeps reordering off for that reason; ax25spec#95 is where it is verified.

## Interpreter changes made for the explorer

All in `codegen/src/Packet.Sdl.Interpreter`, kept to the smallest set that leaves every golden trace's observed effects unchanged:

- `Machine.cs`: `QueueEntry` (label, original N(s), retained payload) replaces the string queue internally (`Queue` still returns labels; `QueueEntries`, `SavedFrames`, `RetainedFrames` are new read-only views); the retained send history is filled on every "I Command" emission and pruned to [V(a), V(s)) after each dispatch (`PruneRetained`); "Push Old I Frame onto Queue" / "Push Old I Frame N(r) on Queue" go through `QueueInsertOld`; `Dispatch` routes a popping old frame in Connected/TimerRecovery to `RetransmitOldFrame` (pinned semantic 1); `DL_DATA_indication` carries the delivered label via a `_deliverData` scratch set by "Retrieve Stored V(r) I Frame"; a private copy constructor and `Clone()`.
- `Effects.cs`: `FrameEffect` gains an optional `Data` (payload label), `UpperEffect` an optional `Detail`; both render the extra field only when present.
- The `vr_lt_ns_lt_vr_plus_k` atom binding (`NsInReceiveWindow`) is main's.
